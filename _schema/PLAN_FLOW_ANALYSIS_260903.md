### 2-6. ⑥ 130 세트입고제외 ★미구현 (판별조건 미확정)

레거시 화면 실측(자도번 `MJU66478801` 조회)으로 구조는 확인:

- 어떤 제번은 **자재가 자기 이름으로 도번 행**이 됨 (13제번 · 소계 126)

#### ★판별조건을 찾았다 (2026-09-03 새벽, 예외 0건)

**상위도번의 `part_plan_ymd` 가 조회 기준일보다 뒤면 자재가 자기 이름으로 선다.**

| | 자기행 13제번 | 미표시 11제번 |
|---|---|---|
| 자재 part_plan_ymd | 260902 | 260902 |
| **상위도번 part_plan_ymd** | **260903 (기준일 초과)** | **260901·260902 (기준일 이하)** |
| 자재 plan_ymd | 260904 | 260902·260903 |
| item_code | 전부 `-S1-2` 파생 | 동일 |
| bom_level | 1 | 1 |
| 상위 파트별계획 존재 | 있음(proc_seq=1) | 있음 |
| 상위 2096 소요 | 있음 | 있음 |

**13/13 · 11/11 예외 없이 갈린다.** 구조도 말이 된다 —
자재 소요일은 오늘(260902, 당일이전 칸)인데 **상위는 아직 안 왔다(260903)**.
상위 행이 화면에 못 서니 그 자재를 실을 데가 없다 → **자재가 독립 행이 된다.**
이것이 "하위→상위품에 속하는 품번의 합계를 단품화"(사용자 설명)의 실제 동작이다.

```
판별식 (제안)
  세트제외 자재 M 의 (제번 W, 상위 U) 조합에 대해
    U 의 plan_part_dtl.part_plan_ymd (proc_seq=1) > 조회기준일   →  M 이 자기행
    그 외                                                      →  U 행에 실림
```

#### ⚠ 교차검증 결과 — 조건을 **단독으로는 쓸 수 없다**

일반 자재(세트제외 아님)에도 같은 조건을 적용해 봤다:
```
미래정밀 · 세트제외가 아닌 자재 155행 중  →  "상위 미래" 81행 (16품목)
```
**"상위 part_plan_ymd > 기준일"은 세트제외 특유의 조건이 아니다.**
따라서 반드시 **`set_except='1'` AND 상위미래** 두 조건을 함께 걸어야 한다.

다른 업체에도 자기행 후보는 존재한다(같은 방식으로 계산):
```
5210A22409B / 2040   18건 566      3A00375P / 2136   16건 312
4A00114D  / 2202   17건 216      MJU66478801 / 2096  13건 126  ← 레거시 화면과 일치
5210A23376A / 2266  13건 107      MJX61537805 / 2111  13건 252
```
`MJU66478801` 이 정확히 **13건 126** 으로 나와 레거시 화면값과 맞는다.
다만 **다른 자재는 레거시 화면 실측값이 없어 검증하지 못했다.**

⟹ 현재 `_SETEXC_ON = False` 로 **꺼 둔 상태**이며, 위 조건은 **가설이지 확정이 아니다.**
   적용하려면 대원산업·케이비 화면에서 세트제외 행을 한 건이라도 실측해 대조해야 한다.

계획(일자별 소요)은 전부 일치한다. LOT만 다르고, 원인은 컬럼 부재다:
```
레거시 PR_T_PLAN_PART_MAT   … PART_PLAN_QTY, LOT_QTY, PLAN_QTY …   ← 소요행이 LOT 보유
웹    nx.plan_part_mat      … part_plan_qty                        ← LOT_QTY 없음
```
없으니 `plan_part_dtl` 에서 조인해 추정하는데, (제번·도번·품목)이 유일키가 아니라 어긋난다.
실측으로 웹 현행 방식이 정확히 1,686(제번·도번 MAX)을 만들고 레거시 소요행 LOT 합은 2,026.

## 3. ★근본 원인 — "하나 고치면 다른 게 깨지는" 구조

### 3-1. 오늘 실제로 터진 것

```
레거시  PR_T_PLAN_ITEM_DTL  (한 테이블)

          └ ORG_PLAN_YMD  = 원본      → 040 이 읽음

          └ 040 을 맞추려 원천을 원본일자로 바꿈

             → AJJ76617501(대원산업 납품)이 화면에서 사라짐
```
조치 완료: 뷰를 화면별로 분리(580=`v_plan_item_dtl_new` / 040·050=`v_sale_plan_item_050`).
**같은 종류가 더 있는지가 문제다.**

### 3-2. 아직 남은 같은 패턴 — 위험도 순

| # | 대상 | 상황 | 위험 |
|:--:|---|---|:--:|
| 1 | **`nx.v_plan_part_copy_new`** | 뷰 **1개 × 화면 4개** (410 · 키팅 · 420 · 580) | ★★★ |

이 뷰의 `PART_PLAN_YMD` 정의는 2026-08-26 에 이미 한 번 바뀐 이력이 있다.

### 3-3. 구조적 원인 — 변경이 눈에 안 보인다

`nx.v_sale_plan_item_050` · `v_sale_plan_050` · `v_plan_input_050` 은
**저장소에 `.sql` 정의가 없다. DB에만 존재한다.**

⟹ 오늘 같은 "뷰 원천 바꿈"이 **git diff 에 안 잡히고 코드리뷰도 못 한다.**
이것이 사고가 조용히 나고 뒤늦게 발견되는 진짜 이유다.

### 3-4. A/S 이중계상 — 잠복 위험

```
웹    nx.plan_item_dtl 의 A/S 제번 333 → STEP5 에 이미 섞임 (52,261)
라이브 PR_T_PLAN_ITEM_DTL 의 A/S      → 0건 (완전 분리)
```
레거시는 LG계획과 A/S를 **절대 섞지 않고 화면에서 UNION** 한다.
웹은 STEP5에 미리 합쳤는데, **580 SP와 040은 예외생산을 또 UNION** 한다.

지금은 SP의 `IN_CUST_CODE > ''` 필터가 우연히 막아 표면화되지 않았고
(580 결과 320행·12,842로 레거시와 일치),
040 정본 `sale_plan_item` 에는 A/S가 0건이라 안전하다.
**그러나 필터 조건이 바뀌는 순간 A/S가 두 번 잡힌다.**
