# ★ 오늘 작업의 뿌리 — 재고가 화면마다 달랐던 이유

오늘 고친 것 중 절반이 재고 문제인데, **원인이 하나로 이어진다.** 먼저 그 구조를 설명한다.

## 1) 재고는 3층이다

| 층 | 테이블(자재 기준) | 성격 |
|---|---|---|
| ① 원장 | `nx.stock_ledger` | 웹 자체 이력. 레거시에 대응물 없음 |
| ② **잔액** | `nx.PU_T_MAT_STOCK_WH` | **실시간 현재고.** 입·출고 때마다 갱신 |
| ③ 미러이력 | `nx.PU_T_STOCK_MAINT` | 레거시 수불이력 미러 |

생산은 `PR_T_MAT_STOCK_WH`, 완제품은 `SA_T_ITEM_STOCK` 이 ②에 해당한다.

**한 층만 쓰면 화면마다 값이 갈린다.** 예를 들어 원장에만 기록하면
준비등록 팝업(스냅샷+원장)에는 보이는데 자재입출고현황(미러이력)에는 안 보인다.

## 2) 문제 A — 쓰기가 3층을 다 안 채웠다

오늘 같은 패턴이 **세 군데**에서 나왔다.

```
자재입고     원장만 기록 → 자재입출고현황에 안 보임      (9/7 대표님이 이미 발견)
세트수동입고  원장만 기록 → 단품재고가 안 늘어남
판매출고     원장만 기록 → 재고가 안 깎임
```

각각 `_WH`(잔액)와 미러이력 쓰기를 추가했고, 이미 어긋난 데이터는 보정 스크립트로 맞췄다.

## 3) 문제 B — 읽기가 화면과 게이트에서 서로 다른 축을 봤다

이게 더 컸다. **잔액(②)이 실시간 정본인데, 여러 곳이 ①③으로 재계산**하고 있었다.

재계산 방식은 `기초 스냅샷 + 그 이후 전표 전부` 인데, 여기 함정이 있다:

- **기초 스냅샷이 고정이다.** 생산은 `stock_yymm='2502'` 하드코딩이고, 실제로 그 테이블엔 2502 한 달치(1,700행)뿐이다.
  즉 **3년 반치를 매번 다시 더한다.**
- 그 긴 누적 어디서 한 번 어긋나면 **오차가 영구히 남는다.**
- 스냅샷 자체가 음수인 품목도 있다.

그 결과가 이렇게 나타났다:

| 증상 | 화면 | 게이트/재계산 |
|---|---|---|
| 자재출고가 거부됨 | 3H00627L 재고 **127.10** | 가용 **−72.50** (260831 일마감 기초가 −72.50) |
| 생산입출고현황 값 불일치 | 잔액 기준 | BF+이동 재계산 — **53조합** 차이 |
| 제품입출고현황 과거일자 | — | 종료일과 무관하게 항상 잔액 → 어제 조회가 오늘값 |

## 4) 그래서 정한 규칙 (대표 확정)

> **조회 종료일이 오늘이면 실시간 잔액, 과거면 이력합계.**
> 그리고 **게이트(출고 가능 판정)는 화면이 보여주는 재고와 같은 값**이어야 한다.

레거시가 원래 그렇게 동작한다. 이 규칙을 자재·생산·완제품 3축에 모두 적용했다.

| 축 | 오늘(실시간 잔액) | 과거(이력합계) |
|---|---|---|
| 자재 | `nx.PU_T_MAT_STOCK_WH` | `nx.PU_T_STOCK_MAINT` |
| 생산 | `nx.PR_T_MAT_STOCK_WH` | `nx.PR_T_STOCK_MAINT_MAT` |
| 완제품 | `nx.SA_T_ITEM_STOCK` | `nx.SA_T_STOCK_MAINT` |

## 5) 문제 C — 세트재고는 만드는 코드가 아예 없었다

3층 얘기와 별개로, **가공세트재고는 웹에 증가(+) 코드가 없었다.**
차감(−)만 구현돼 있어 레거시가 만들어 준 것에 의존하고 있었다(§4에 상세).

## 4. ★가공세트재고 — 웹에 **만드는 코드가 없었다**

**증상** 580 에서 전표 61개 발행→입고확인 했는데 `이동전표발행` 칸이 비었다.

**원인**
```
nx.PU_T_SET_GAGONG_STOCK : 양수 445행 · 음수 0행
그 445행 전부 레거시(w_pu_stock_057_2 · SP_PR_SET_가공세트재고)가 만든 것
웹은 prodsheet.py:987 에서 **차감(−)만** 한다 → 만드는(+) 코드가 아예 없다
```
라이브에는 레거시가 11:09 에 만든 61 이 있었으나 nx 미러에 아직 안 왔다.
**레거시가 은퇴하면 만드는 쪽이 사라져 세트재고가 영영 안 생긴다.**

`stock.py:866` 주석이 "차감은 생산실적에서 한다"고만 적고 **증가를 안 넣은 것**이 원인.
레거시 `w_pu_stock_057_2` 는 MERGE 로 증감을 함께 한다.

**조치** `stock.py` 입고확인 루프에 증가(+) 신설.

**규칙(라이브 실측 9월 40건 전수 일치로 확정)**

| 항목 | 값 |
|---|---|
| 시점 | 입고확인(`IN_CONFIRM_FLAG='1'`) 과 같은 트랜잭션 |
| 이력 | `nx.PU_T_SET_STOCK_MAINT_GAGONG` `MAINT_TAG='2'` **양수** |
| 잔액 | `nx.PU_T_SET_GAGONG_STOCK` + |
| 키 | **도번(`ITEM_CODE`)** — 자도번 아님 |
| 거래처 | `SAGUB_CUST_CODE` 있으면 그 사급처, 없으면 `'Z99990'` |
| 수량 | 전표 `SET_QTY`(= `IN_MAINT_QTY`, 실측 동일) |
| 단위 | **(그룹, 도번, 거래처)당 1행** — 전표가 3행이어도 세트이력 1행 |

**검증(롤백 보장, DB 변경 0)**
```
단일행  AJR74844312 SET=10  → 세트재고 +10 · 이력 +10 · seq=20000 ✅
복수행  AJR72946806 자도번 4행 SET=3 → 세트재고 +3 · 이력 1행 ✅
        (자도번별로 넣었다면 12가 됐을 것 — 도번 단위 집계가 핵심)
검산    AJR76164202 라이브 tag'2' +1,827 − tag'P' 1,766 = 61 = 잔액 61
```

이로써 흐름이 닫혔다: `전표발행(미확정) → 입고확인(확정+세트재고 생성) → 생산실적(차감)`.

## 6. ★가공창고 이동계획(580) — 조회를 웹버전으로

### 방침 — 대표 확정
① 값은 **지금 SP와 100% 같아야 한다** ② SP 안의 **버그성 동작도 그대로 복제** ③ 범위는 **조회만**

### 그대로 복제한 SP 버그 4개 (고치면 diff 발생)

| # | 위치 | 내용 |
|---|---|---|
| B1 | SP 253 vs 260~264 | ASSY커서 `ORDER BY` 에 `BOM_LEVEL` 이 없는데 키 비교엔 있다(올바른 정렬은 254행에 주석처리) → 재고 반복 리셋 |
| B2 | SP 588 | 도번고정커서 `WHERE` 가 `STOCK_QTY+PR_STOCK_QTY+FIX_STOCK_QTY>0` 인데 앞 둘은 646행에서야 채워진다 → 실질 `fix_stock_qty>0` |
| B3 | 전 커서 | 커서 그룹키 ≠ UPDATE 8키. **T-SQL 커서는 연 시점 스냅을 본다**(실측 확인) → 중복 가산 |
| B4 | 커서별 | `use_qty` 곱셈이 제각각 — 출하○ ASSY○ 도번고정✕ 자재✕ 파트✕ |

B3 은 추측이 아니라 실측했다: 임시표 3행(finish=0)에 커서를 돌며 매회 전행 +1 → fetch 값 `0,0,0`
(갱신값을 봤다면 `0,1,2`).

### 파라미터 함정(SP 실측)
- `from_ymd` = **필터 아님**. 32칸 피벗 앵커(`_00`=미만 전부, `_01`=+0일 … `_31`=+30일)
- `to_ymd` = 유일한 실제 필터. **하한 없음**
- `pr_part_code`·`sagub_cust_code` = **죽은 파라미터**(SP 450~453·534~537 전부 주석)

### 검증 — diff0 게이트 `_migration/move580_diff.py`
```
P2 260908~09  SP 239행 / 웹 239행  174컬럼 × 239 =  41,586 비교  불일치 0
P1 260908~09  SP 464행 / 웹 464행                 80,736 비교  불일치 0
```

비교는 순서가 아니라 **키**로 맞춘다(SP 최종 SELECT 에 ORDER BY 가 없어 순서가 비결정적).

### 구현 중 잡은 실제 결함

## 9. 조사만 하고 **바꾸지 않은 것** — 4주간 가공계획현황

`PR_T_PLAN_PART_DTL_FOR_CUST` 는 **레거시 STEP6 배치가 TRUNCATE+복제로 만드는** 테이블이고

```

```
그래서 5브랜치를 그대로 옮기면 **A/S가 두 번 계상**된다(`PQ060905R01.AKOR` 4,000 → 8,000).
