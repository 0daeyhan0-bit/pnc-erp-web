## 1. 준비등록(키팅) BOM 축 전환 — CS 미러 → 클린

### 1-1. 문제 — 화면과 준비등록이 서로 다른 BOM 을 보고 있었다

```
품목 BOM관리 화면   편집 →  nx.bom_line        (클린)
준비실적처리(키팅)   조회 →  nx.CS_M_ITEM_BOM   (원가 BOM 미러)   ★다른 테이블
```

화면에서 소요량·투입파트·키팅 체크를 고쳐도 준비등록은 다른 테이블을 읽으니
반영되지 않는다. 컷오버(§1-9-1)에도 죽는 코드다.

`ready.py` 종전 주석은 이렇게 되어 있었다:

> ★BOM 소스 = CS_M_ITEM_BOM(웹 정본). 레거시 화면은 PR_M_ITEM_BOM을 쓰지만
> **실측 결과 두 테이블이 동일**(자도번·USE_QTY·KITTING_FLAG 일치)이라 …

**그 전제가 지금은 깨져 있었다.**

### 1-2. 판정기준 = 라이브 `PR_M_ITEM_BOM`

어느 쪽이 맞는지는 웹끼리 비교해선 알 수 없다.
**라이브 생산BOM(정본, `PARTNER_ERP.dbo.PR_M_ITEM_BOM`)** 을 심판으로 세워 전수 대조했다.
비교 조건은 `ready.py` 가 실제로 쓰는 것 그대로 — 전개제외≠1 · 사용수량>0 · 유효기간.

| 항목 | 결과 |
|---|---|
| 행수 | 클린 **35,380** ≡ 라이브PR **35,380** / CS 35,350 (30행 부족) |
| 사용수량 차이 34쌍 | **클린 맞음 30** · CS 맞음 3 · 둘다 다름 1 |
| 투입파트 차이 289쌍 | **전부 클린이 맞음 (100%)** |
| 클린에만 329쌍 | **329/329 전부 라이브PR 에 존재** = CS 가 빠뜨린 것 |
| CS 에만 227쌍 | 223쌍은 라이브PR 에도 없음(CS 전용 잔재) |
| " 나머지 4쌍 | 라이브PR `KITTING_FLAG=0` 인데 CS 만 1 → 원래 키팅대상 아님 |
| **클린 결손** | **0건** |

실측 예 — `AJR30157301` (레거시 화면 24구성으로 눈으로 확인):

```
자품번          클린nx   nxCS   nxPR   라이브PR   레거시화면
3H01582A          2       5      2       2         2
3H01582E          5       2      5       5         5
```

**CS 에서만 A 와 E 의 수량이 뒤바뀌어 있었다.** 즉 준비등록이 그동안
3H01582A 를 5개(정답 2개), 3H01582E 를 2개(정답 5개)로 잡고 있었다.

투입파트도 같은 양상:
```
5211A22074A-2 → 4A00742A       CS=S11  클린=RAC  라이브=RAC
ADM74790617   → ADM74790602-*  CS=S8   클린=S9   라이브=S9
```
파트가 틀리면 재고를 옮길 파트창고가 달라진다.

전체 289쌍 = `_out_투입파트차이289_260908.csv`

### 1-3. 조치

`ready.py` `_SQL` 한 곳만 교체. **컬럼 별칭을 그대로 둬서** 아래 전개 로직
(가상도번 재전개 · 파트 필터 · KITTING_FLAG · excluded 처리)은 한 줄도 안 바꿨다.

```
FROM nx.CS_M_ITEM_BOM a
  ↓
FROM nx.bom_line l JOIN nx.bom_header h ON h.bom_id=l.bom_id
```

- `bit`(except_flag/kitting/vir_item) → 종전 varchar `'0'/'1'` 의미로 캐스팅
- 품목명·협력사 조인(`nx.item`)은 종전 그대로 — 이미 클린이었다

### 1-4. ★함정 — `from_ymd`/`to_ymd` 는 빈 문자열이다 (NULL 아님)

```sql
-- 틀림: NULL 만 보면 빈 문자열('') 행이 통째로 오탈락한다
(l.from_ymd IS NULL OR l.from_ymd<=@d)

-- 맞음
ISNULL(NULLIF(LTRIM(RTRIM(l.from_ymd)),''),'000000')<=@d
```

`nx.bom_line.from_ymd/to_ymd` 는 `nvarchar` 이고 **빈 문자열이 다수**다
(NULL 은 770/763행뿐). 처음 측정에서 이걸 놓쳐
**"234쌍이 사라진다"는 잘못된 결과**를 냈고, 대표님이 레거시 화면을 보여주며
"레거시하고 똑같이 편성되어 있는데 왜 빠진다는거지?" 라고 지적해 바로잡았다.
조건을 고치니 방향이 정반대였다 — 사라지는 게 아니라 **틀린 게 고쳐지는 것**이었다.

### 1-5. 세트제외는 여기서 거르지 않는다 (재삽질 방지)

`SET_EXCEPT_FLAG` 는 **BOM관리 표시용**이고 키팅·편성의 제외조건이 아니다.
- 레거시 466 목록에 세트제외='1' 품목(5210A23376A 등)이 그대로 나온다
- 걸렀더니 26→24 로 2건 모자랐다(실측 반증)
- 쓰는 곳은 `setinstat.py`(세트입고) · `coopplan.py`(협력사) 뿐

계획 편성(`planrev.py`)에도 `set_except` 는 한 번도 안 나온다.
편성이 쓰는 두 플래그는 `except_flag`(현행경로) · `cs_calc_except`(원가제외).

### 1-6. 계획 편성은 이미 클린이다 — 손댈 것 없음

`v_pr_bom` 뷰가 `bom_header`+`bom_line`+`proc_weld` 를 UNION 한 것이라
STEP6·STEP7 은 이미 클린을 읽는다. **미러 직독은 준비등록 하나뿐이었고 이번에 없앴다.**

## 5. 라벨 프린터 한글 출력 (옆 세션 작업, 같은 커밋)

TSPL 의 `TEXT` 는 **프린터 내장 폰트**로 찍는데 내장 폰트("1"~"5")가 ASCII 전용이라
한글이 통째로 누락됐다 — 현장 라벨에 용접사/검사자가 `/` 만 찍혔다.
`CODEPAGE UTF-8` 을 줘도 **글리프 자체가 없다**. 같은 데이터를 PDF 로 뽑으면
맑은 고딕이 embed 돼 멀쩡히 나온다 ⟹ 데이터·좌표가 아니라 **폰트 문제**.

- 그 줄만 서버에서 1비트 비트맵으로 그려 `BITMAP x,y,width_bytes,height,mode,<raw>` 로 전송
- **TSPL 은 비트 1=흰색, 0=검정 (반전)** — 그대로 보내면 배경이 새까맣게 나온다
- 프론트는 `b64` 플래그를 함께 넘긴다. 빠지면 에이전트가 평문으로 해석해
  utf-8 로 재인코딩하고 비트맵이 깨진다.

## 6-2. 포장·작업자 4종 클린 전환 (커밋 `2ccaddd`, 옆 세션)

### 무엇을

포장종류·포장수량·용접자(생산자)·검사자 — 레거시 「품번별추가정보」(w_pr_master_080).
**라벨(제품스티커)·가간판이 이 값을 찍는다.**
생산정보등록 화면에서 편집하도록 하고, 저장은 항상 클린 `nx.item_sub`
(공용 헬퍼 `prodinfo.save_item_pack`).

`save_item_pack` 은 **`None` 인 항목을 건드리지 않는다**(부분수정 허용).
라벨 재발행 팝업은 용접사·검사자만 주는데, 전체 UPDATE 면 포장정보가 지워진다.

### ★선행 교정 — `item_sub` 덮어쓰기 사고

품목마스터 저장이 `nx.item_sub` 를 **DELETE→INSERT** 하고 있었다.
그런데 `nx.item_sub` 는 13컬럼인데 그 화면이 보내는 건 8개(`_SUB_STR`+`_SUB_INT`)뿐이다.

```
나머지 5개(pack_kind·prod_worker·insp_worker·lg_obtain_flag·min_pur_qty)가
행이 통째로 지워졌다 재삽입되며 NULL 로 날아갔다.
```

`item.py` 머리말(:34)이 이미 "저장 미터치·데이터 보존" 이라 적어둔 항목들인데
**구현이 그 약속을 어기고 있었다.** 같은 행을 두 화면이 나눠 쓰게 되므로,
이걸 먼저 고치지 않으면 생산정보등록에서 넣은 값이 품목마스터 저장 한 번에 사라진다.

⟹ 행이 있으면 **내 컬럼만 UPDATE**, 없을 때만 INSERT.

### 라벨·가간판 소스 = 항목별 단일소스

```

```
폴백이 아니라 **항목별로 소스가 하나씩**이다(§1-9-1 준수).
미러 전용 2종도 편집화면이 생기면 클린으로 옮겨야 컷오버에 안 죽는다(잔여 부채).

### ⚠한시적 폴백 — 조회는 클린 우선·미러 폴백

§1-9-1(폴백 금지) 위반이지만 지금은 불가피하다:

