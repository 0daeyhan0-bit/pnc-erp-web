## 1. 세트입고현황 `setinstat/list` — 88초 → 26초 (커밋 `257f6ea`)

**원인은 쿼리가 아니었다.** 주 쿼리(①②③ UNION)는 1.3초로 멀쩡했다.

```
① 파트별 생산계획  1.6s / 34,285행      ② 직납품 0.1s      ③ 세트입고제외 0.1s
①∪②∪③ 합본       1.3s / 40,891행
```

느린 곳은 그 뒤 **조회 루프 3곳**이었다. `(work_order=? AND item_code=?)` 를 **400개씩 OR 로
이어붙여** 청크마다 돌린다. OR 나열은 SQL Server 가 인덱스 탐색으로 못 풀어 **청크마다 테이블을
통째로 훑는다.**

```
키 7,088개 = 18청크 × 1.2초 = 21.9초     ← 이 패턴이 3곳(계획·직납폴백·출하실적)
```

**수정** — `_keytmp()` 신설. 키를 임시테이블(PK)에 담고 `EXISTS` 조인으로 한 번에 조회.

```
단독 대조 : 400-OR 21.9초 → 임시테이블 4.1초 · 결과 7,088행 완전 동일
전체      : 88.3초 → 25.3초 · 8,686행 · (제번,도번) 키집합 완전 동일
```

### 1-1. 같이 잡은 순서 의존 결함 (`assy`)

`det.setdefault(...)` 가 **먼저 온 행이 이기는** 구조인데 주 쿼리에 `ORDER BY` 가 없다.
⟹ **같은 데이터인데 실행계획이 바뀌면 값이 바뀐다.**

```
실측 MBL68420201 : AJR30028411 / AJR75802613 사이에서 흔들림
수정(최대값 고정) 후 : 5회 연속 동일 해시
```

배포본이 지금 보여주는 값도 "우연히 안정적일 뿐" 보장된 값이 아니었다.

### 1-2. ☐승인 대기 — `jcust` 도 같은 순서 의존

일부러 **손대지 않았다**. 화면 값이 바뀌는 변경이라 혼자 정하지 않는다.

| 바꾸는 방식 | 달라지는 행 |
|---|---|
| 최대값으로 고정 | **1,848행** |
| 빈칸만 채우기 | **12행** (`''` → `2111 삼화코리아` 등) |

데이터에는 작업처가 있는데 화면은 빈칸으로 보이는 건들이다. 어느 쪽이 맞는지 확인 필요.

## 2. 매출마감 중량정산 `salemagam/weight` — 53초 → 2.6초 (커밋 `8840f83`)

```
맵 적재 _load_maps        6.9초
쿼리 3개                  2.7초
★소요엔진 전개 루프       56.9초   ← 전부 여기
```

전개는 입고품목 **1,492종**을 엔진에 묻는다(1건당 33ms). **엔진이 그 답을 캐시한다** —
같은 1,492종을 두 번째로 물으면 **0.0초**. 즉 **프로세스당 1회 비용**이지 매번 드는 비용이 아니다.
memo 로는 못 줄인다(입고 1,494행 중 품번 중복 2건뿐).

**수정** — 기동 예열 스레드에 `compute(당월)` 1회 추가. `weight_calc.py`·`salemagam.py` **무변경**.

```
예열(백그라운드) 57.2초  →  ★예열 후 첫 사용자 조회 2.6초 · 25행
```

## 3. 원가 LG비교 `cost/lgcompare` — 매번 41초 → 재호출 1.4초 (커밋 `5c66f83`)

성격이 달랐다. 이 엔드포인트는 `NxCostEngine()` 을 **매 요청 새로 만들고 `finally` 에서 닫았다.**
그래서 캐시가 매번 버려지고, 다른 원가 화면이 데워 둔 것도 못 썼다.

```
naewon 20건 38.3초 + naewon_lg 4.0초 = 42.3초
같은 20건을 한 번 더 → 1.3초          ← 차이가 전부 엔진 캐시
```

**수정** — 공용 싱글턴 `common._get_cost_engine()` 을 `_COST_LOCK` 아래서 사용(닫지 않는다).
`close.py _bom_engine` 이 **같은 문제를 같은 방법으로 이미 고쳐 둔** 패턴이다(거기 실측 30.5초 → 0.7초).

```
배포본 1회 41.2초 / 2회 40.9초   (매번 콜드)
수정본 1회 29.5초 / 2회  1.4초
★결과 완전 동일 (diff 0) — 원가 하드룰 충족
```


## 5. 자재예상매입 `matexpect` — 동시조회 충돌 제거 + 예열 (커밋 `cb390af`)

### 5-1. 동시에 열면 서로 막는다 (진짜 결함)

공유 캐시테이블 `nx.item_mat_soyo` 를 **읽고 쓴다.** FastAPI 는 sync 엔드포인트를
스레드풀에서 돌리므로 동시 조회가 실제로 겹친다.

- `_ensure_soyo_cache` 의 `TRUNCATE` 가 상대 적재를 지우고
- `_soyo_of` 의 `INSERT` 가 같은 키로 부딪힌다(PK)

실측: 서버 3대를 동시에 물렸더니 **19초짜리가 300초를 넘겼다**(§0 의 헛발이 이걸 드러냈다).

**수정** — `_SOYO_LOCK` 으로 캐시 구간만 직렬화. 뒤에 온 요청은 앞사람이 채운 캐시를 그대로 읽는다.

```
4스레드 동시 : 전체 4.9초(스레드별 2.8~4.8초) · 예외 0
3스레드 결과 : 키집합·전 필드값 완전 동일(3,516건)
```

★처음에 "동시 결과가 다르다"고 본 것은 **리스트 정렬 순서까지 비교한 탓**이었다.
  동점 정렬 순서만 다르고 값은 같다.

### 5-2. BOM 이 바뀌면 다음 첫 조회가 197초

서명가드가 캐시를 통째로 비운다(stale 차단 = **정확성 조건이라 유지**).
비면 완제품 565종을 엔진에 다시 물어 채운다 — 197초. 채워져 있으면 2.5초.

**수정** — 기동 예열에 `matexpect()` 1회 추가(재시작 직후 첫 사용자 보호).
☐낮에 BOM 을 고치면 그 뒤 첫 조회는 여전히 재빌드를 문다(구조상). 다만 락 덕에 **한 사람만** 문다.
