### 0-1. 레거시는 어떻게 하고 있나
- **현재고** `PU_T_MAT_STOCK_WH` = 전표 저장 시 **실시간** upsert(`f_pu_set_mat_stock_wh`). 실측 마지막 갱신 = 당일 07:39
- **월마감 스냅샷** `PU_T_MONTH_STOCK_WH` = 진짜 저장소(19개월 2412~2607)
- **일수불** `PU_T_MONTH_STOCK_WH_DAILY` = 조회용 임시테이블(TRUNCATE 재생성)
- **일마감/월마감은 "잠금"** — `CM_M_DAILY_MAGAM`(gubun '1', 현재 **260812**) 이전 일자는 재고변경 차단, 예외테이블 `CM_M_DAILY_MAGAM_EXCEPT`, MASTER 계정만 강행
→ 즉 **레거시도 "마감=잠금"이 맞고**, 스냅샷 생성은 월마감 산출물이 담당한다.

## 1. ★우리 로직

### 1-1. 마감의 정의
**마감 = ① 그 시점 잔량을 스냅샷으로 확정(freeze) + ② 그 기간 재고이동 전표 CRUD 잠금.**
해제(reopen)는 **확정 스냅샷 제거 + 잠금 해제 + 로그**.

### 1-2. 스키마 (`_migration/create_period_close.py`, 멱등)
```
nx.period_close    domain(MAT/PRD/SAL) · ptype(D일/M월) · period(YYMMDD | YYMM)
                   close_flag · close_user/close_dt · reopen_user/reopen_dt · note
                   PK(domain, ptype, period)
nx.stock_snapshot  domain · ptype · period · item_code · stock_qty/amt · avg_cost · in/out_qty · close_dt
                   PK(domain, ptype, period, item_code)
```

### 1-3. ★자재 스냅샷 소스 = `nx.mat_stock_daily` (검증으로 확정)
**검증(2026-08-27, 읽기전용 전수대조)** — 우리 일별잔량 월말값 vs 레거시 `PU_T_MONTH_STOCK_WH`

| 기준월 | 공통 품목 | 수량 일치 | 우리만 | 레거시만 |
|---|---:|---:|---:|---:|
| 2606 (260630) | 2,342 | **2,342 (100.00%)** | 0 | 1,409 |
| 2607 (260731) | 2,534 | **2,534 (100.00%)** | 10 | 1,195 |

"레거시만" 1,195품목은 **전부 재고 0·금액 0** → 커버리지 갭 무해.
∴ **마감 시 `mat_stock_daily` 의 해당 시점 잔량을 그대로 확정하면 된다.**

**역할 분리**: 빌더(`matclose_movavg_build.py`)=매일 일별잔량 전개 / 마감=그 시점 값을 **확정 + 잠금**. 빌더를 마감이 대체하지 않는다.

### 1-4. ★기존 `/api/stockclose/*`(Phase5, 원장기반)를 쓰지 않는 이유
같은 세션에서 실측 대조:

| 방식 | 레거시 2606과 일치 | 비고 |
|---|---:|---|
| 기존 `/api/stockclose/run`(nx.stock_ledger 기반) | **45.88%** | 기말합계 **−5,892,366**(음수) · `stock_close_snap` **0행**=한 번도 실사용 안 됨 |
| 신규 `/api/close/run`(mat_stock_daily 기반) | **100.00%** | |

충돌표 **C13**("nx.stock_ledger MAT은 미동기 45% 오차로 게이트 source 탈락")과 정확히 일치.
→ 기존 엔드포인트는 **삭제하지 않되 현행 정본 아님**. 원장이 정본이 되는 **컷오버 이후 재검토** 대상.

### 1-5. 가드 (연쇄 무결성)
- **미래 기간** 마감 불가
- **순서 강제**: 직전 기간이 마감돼 있어야 다음 기간 마감 가능(첫 마감은 예외)
- **역순 해제**: 후속 기간이 마감돼 있으면 해제 거부(기초 연쇄의존)
- **중복 마감** 거부
- **재마감 가능**: 해제 후 다시 마감 — `period_close` UPSERT
- **원자성**: 스냅샷 확정과 잠금은 한 트랜잭션(`_nx_tx`)

### 1-6. 공용 잠금 게이트 (전 부서 동일)
```
common._lock_msg(cur, ymd, domain="MAT")   # 사유메시지 or None (비발생형)
   ① 일마감 period_close(domain,'D',YYMMDD)
   ② 월마감 period_close(domain,'M',YYMM)      ← 일마감 ⊂ 월마감
   ③ 하위호환 nx.stock_close(ym)                ← 구 전역 월잠금(기존 동작 보존)

common._assert_open(cur, ymd, domain, what)  # 위가 잠겼으면 HTTP 400 으로 거부
```
**규칙(사용자 확정 2026-08-27): 재고가 조금이라도 움직이면 잠근다. 재고이동과 문서발행을 겸해 분리가 어려우면 → 막는 쪽으로 지정.**

### 1-7. 적용 범위 — 재고이동 쓰기 전수
"재고를 실제로 움직이는가"를 **재고테이블 DML + 원장 헬퍼 호출**로 판별.

| | 적용 전 | 적용 후 |
|---|---:|---:|
| 재고이동 쓰기 엔드포인트 | 39 | 38 |
| 마감잠금 있음 | 23 | **38** |
| **커버리지** | **58%** | **100%** |

신규 적용 16곳: 자재 입·출고(`/api/stock/save` — 구 인라인 잠금을 공용 게이트로 승격) · 사급출고(save/confirm) · 출하실적(save/delete) · 출하처리(sale040/confirm) · 세트입고 · 세트재고조정 · 준비재고(commit/register) · 도입(save_batch/delete) · 가공이동(issue/delete) · 생산재고조정(save/delete).

## 6. ★단가 불일치 근본원인 — 레거시는 총평균법, 우리는 이동평균 (2026-08-27 규명)

### 6-1. 먼저 정정 — "빌더가 정답"이 아니었다
앞서 `260630` 한 지점만 보고 *"빌더 98.6% = 정답, 파생 63.5% = 틀림"* 이라고 판단했으나 **틀린 판단**이었다.
`260630`은 **빌더의 시드 지점**(레거시 2606을 그대로 받은 자리)이라 당연히 일치한다. 한 달을 굴린 뒤를 보면:

| 대조 | 수량일치 | **단가일치** |
|---|---|---|
| 빌더 `260630` vs 레거시 2606 (시드지점) | 100.00% | 98.63% |
| **빌더 `260731` vs 레거시 2607 (한 달 굴린 뒤)** | 100.00% | **78.00%** |
| 파생(기초=레거시2606) `260731` vs 레거시 2607 | 99.92% | **80.17%** |

→ **빌더도 단가는 레거시를 재현하지 못한다.** 파생본이 오히려 근소하게 낫다.
기존 기록의 "mat_stock_daily == 레거시 월마감 100%"는 **수량만**의 이야기였다(수량은 실제로 100.00%).

### 6-2. 진짜 원인 = 회계방식 자체가 다름
레거시 월마감 정본 = **`src_extracted/sa_stock_01/w_pu_stock_160.srw`** (`DELETE`+`INSERT INTO pu_t_month_stock_wh`).

```
STOCK_COST = (BASIC_AMT + INPUT_AMT) / (BASIC_QTY + INPUT_QTY)      ← 월 1회 계산
BASIC = 전월 기말 / INPUT = 그 달 전체 입고 합계
```

우리(빌더·파생 **공통**) 규칙과의 차이 6가지 — 이게 78~80% 불일치의 정체:

| # | 항목 | 레거시 (w_pu_stock_160) | 우리 (빌더 = 파생) |
|---|---|---|---|
| 1 | **평균방식** | **총평균법** — 월 단위 1회 | **이동평균** — 입고 건건 재계산 |
| 2 | **입고 tag** | `3,9,C,G,H,S,P,R` | `9,S` 만 |
| 3 | **검사 미통과 제외** | `NOT (insp_flag IN ('S','F') AND insp_proc_flag<>'1')` | 조건 없음 |
| 4 | **수입 금액원천** | `PU_T_STOCK_MAINT_C.TAXPAYERS`(과세표준) | `MAINT_AMT × EXCHANGE_RATE` |
| 5 | **소모품 제외** | `ISNULL(ITEM_SGROUP,'') < '990'` | `ITEM_SGROUP LIKE '99%'` |
| 6 | **품목마스터 조인** | `JOIN PR_M_ITEM` — 마스터에 없으면 탈락 | 조인 없음 |

(참고: 출고 tag `1,4,5,6,8,A,B,J` · 반납 `T` · 조정 `2` 로 명시 분류. 우리는 "전 tag 부호합"으로 뭉뚱그림 — **수량은 결과가 같아 100% 맞았다**.)

### 6-3. 그래서 결정이 필요한 지점
**수량은 이미 해결**(99.9%~100%, 잔여는 아래 6-4). 남은 건 **단가 = 회계방식 선택**이고 이건 원가에 직결된다.
- (A) **레거시 총평균법 재현** — 원가 diff0 하드룰과 정합. 단, 월 1회 단가라 일마감 단가는 근사치가 됨.
- (B) **우리 이동평균 유지** — 주류 ERP(SAP moving average V) 방식·실시간 원가에 맞음. 단, 레거시 대비 78~80%로 벌어짐 = 원가 diff0 깨짐.
- (C) **분리** — 회계용 월단가 = 레거시 총평균(diff0) / 운영용 일단가 = 이동평균. 둘 다 저장.

## 12. ★확정 회계방식 (2026-08-27, 세무사 확인 후) — 이동평균법 + 저가법

### 12-1. 사실관계 — 레거시가 신고 방법과 다르다

| | 방식 |
|---|---|
| **신고된 평가방법**(세무사 확인) | **이동평균법 + 저가법** |
| **레거시 시스템 실제 계산**(`w_pu_stock_160.srw` 실측) | **총평균법** · 저가법 **없음** |
| 우리가 원래 만들었던 것 | 이동평균법 (레거시와 단가 78% 일치) |

★**"이동평균이 레거시와 78% 밖에 안 맞는다"고 문제로 봤던 것이, 사실은 신고 방법이 맞고 레거시가 어긋난 것**이었다.
⟹ **하드룰 충돌**: "레거시와 diff0" vs "신고 방법 준수" → **신고 방법이 우선**.
⟹ 자재 단가는 **레거시 diff0 대상에서 제외**하고, 차이를 리포트로 상시 노출한다.
※ 원가엔진(`nx_cost_engine`)의 레거시 diff0 하드룰은 **영향 없음** — 원가엔진은 `avg_cost` 를 참조하지 않는다(§9 실측).

**세무사께 추가 확인 필요**: 그동안 재무제표 재고금액이 레거시(총평균) 값으로 작성됐다면
**신고 방법과 다르게 평가해온 것**이 된다. 과거분 처리 방향.

### 12-2. 도메인별 확정 (대표 결정)

| 도메인 | 평가방법 | 단가 기반 |
|---|---|---|
| **자재(MAT)** | **이동평균법** | 매입원가 |
| **생산(PRD, 재공품)** | **이동평균법** | **매입가**(제조원가 아님 — 12-8) |
| **영업(SAL, 제품)** | **이동평균법** | **판가 기반**(대표 재확인 2026-08-27) |
| 전 도메인 | **저가법** 별도 레이어 | 원가 vs 시가(NRV) 중 낮은 값 |

**★영업(SAL) = 판가 기반 이동평균 (대표 재확인)**
"판가도 수시로 업데이트된다"는 지적이 있었으나 **이동평균이면 그 변동이 완화**된다 —
입고 시점 판가로 가중평균되므로 최신 판가 하나가 재고 전체를 흔들지 않는다.

**남는 회계 이슈(재무제표용은 추후 — 대표 지시)**: 판가 기반은 미실현이익이 재고자산에 섞이고
신고한 저가법(원가 vs 시가 중 낮은 값)과 상충한다. **재무제표용 원가 축 + 저가법은 별도 과제**로 미룬다.
지금 만드는 것은 **운영·관리용 평가**다.

### 12-3. 총평균 작업에서 그대로 가져갈 것 (낭비 아님)

평균 계산식만 바뀐다. **분류 축·데이터 원천·제외기준은 전부 유효**하며, 기존 우리 이동평균의 오류를 교정한다:

| 항목 | 기존 우리 이동평균 | **정본(총평균 작업에서 규명)** |
|---|---|---|
| 입고(평균 갱신) tag | `9, S` 만 ❌ | **`3, 9, C, G, H, S, P, R`** |
| 출고 tag | (전 tag 부호합) | `1,4,5,6,8,A,B,J` · 반납 `T` · 조정 `2` |
| 수입 금액 | `MAINT_AMT × 환율` ❌ | **`TAXPAYERS`(과세표준, 이미 원화)** |
| 검사 미통과 | 조건 없음 ❌ | `NOT(insp_flag IN('S','F') AND insp_proc_flag<>'1')` |
| 소모품 제외 | `LIKE '99%'` | **`ITEM_SGROUP >= '990'`** |
| 품목마스터 조인 | 없음 | `JOIN PR_M_ITEM`(미등록 탈락) |
| 품목키 | 원문 | **`UPPER(LTRIM(RTRIM()))`** (CI 콜레이션) |
| 잔량 0 | 적재 | **제외**(대표 확정) |

**★일 단위 묶음 = 건별과 동일**: 이동평균은 원칙상 입고 건건 재계산이지만,
`(q0·a0 + Σamt)/(q0 + Σqty)` 는 순차 적용과 결과가 같고, 출고는 평균을 바꾸지 않으므로
**같은 날 여러 전표를 묶어도 건별과 동일**하다. 일 단위 전개로 충분하다.

### 12-4. 저가법 — 신설 필요(현재 시스템에 전혀 없음)
```
평가액 = MIN(취득원가(이동평균), 순실현가능가치(NRV))
평가손실 = 취득원가 − NRV  (NRV < 원가 일 때)
```
**NRV 기준을 정해야 한다(미결)**:
- 원소재 = LME/시세(`nx.price_metal` 보유)

- 장기체화·불용 = 무이동 기간별 감액률

→ **세무사께 NRV 산정 기준 확인 필요.** 금액을 크게 좌우한다.

### 12-6. ★레거시 생산재고 평가방식 규명 (2026-08-27)

정본 = `src_extracted/sa_stock_02/dw_pr_stock_480_t2.srd` (생산재고조회 480 데이터윈도).

```
생산재고 금액 = stock_qty × item_cost2
item_cost2 = pr_m_item_cost.item_cost
             WHERE cost_tag='1'                                  ← 매입단가
               AND cost_apply_ymd <= :as_from_ymd                ← ★조회 '시작일' 기준 최신
               AND cust_code = CASE WHEN m.work_code='P2' THEN '2228' ELSE m.in_cust_code END
             ROW_NUMBER() OVER(PARTITION BY item_code,cust_code ORDER BY cost_apply_ymd DESC) = 1
```

**⟹ 레거시 생산재고에는 평가방법이 없다.** 품목마스터의 **매입단가 스냅샷을 그대로 곱할 뿐**이다.
이동평균도 총평균도 아니고, 굳이 분류하면 **최종매입원가법에 가깝다**.

**문제 3가지**
1. **신고 방법(이동평균법) 미적용** — 평가방법 자체가 적용돼 있지 않다.
2. **가공비·노무비가 전혀 반영되지 않는다** — 재공품인데 **원재료 매입가로만** 평가한다.
   재공품은 투입된 제조원가(재료비+가공비)로 평가해야 한다.
3. **조회 기간을 바꾸면 금액이 바뀐다** — 단가 기준일이 `as_from_ymd`(조회 시작일)라
   같은 시점 재고인데 조회 조건에 따라 평가액이 달라진다. **재무제표 값이 될 수 없다.**

※ 레거시 `PR_T_MONTH_STOCK_WH`(생산 월마감)는 **2502 한 달치뿐** — 그 뒤로 생산 월마감을 하지 않는다.
   즉 생산재고에는 **확정된 기말 평가액이 존재하지 않는다.**

**⟹ 우리 방향(생산 = 제조원가 기반 이동평균)이 옳다는 강한 근거.**
레거시와의 diff0 은 애초에 성립하지 않는다(레거시에 확정값이 없다). 대조는 **수량 축**으로만 한다.

### 12-8. ★생산재고 = **매입가 기반** 이동평균 (대표 결정 2026-08-27)

제조원가(재료비+가공비) 기반으로 하려다 **매입가 기반**으로 확정했다.

**채택 근거 — 실측 3가지**

| 근거 | 실측 |
|---|---|
| ① **가공비를 전 품목에 일관 적용할 수 없다** | 생산재고 **795품목 중 라우팅 보유 557 (70.1%)**. 나머지 30%는 UPH 가 없어 가공비 산출 불가 → 같은 재고에 **70% 제조원가 + 30% 매입가**가 섞여 **일관성이 깨진다**. 반쪽 제조원가보다 **일관된 매입가**가 낫다 |
| ② **지금 목적은 운영·관리용** | 재무제표용 제조원가 평가 + 저가법은 **별도 과제로 보류**(대표 지시) |
| ③ **구현·성능** | 자재와 **같은 엔진**(`_mv_step`) 재사용. 원가엔진 호출이 없어져 마감 성능도 개선 |

**★"생산 저평가 + 영업 고평가가 상쇄된다"는 근거로 삼지 않는다 — 기록에 남긴다**
- 규모가 다르다: 2607 생산 **457,999,957** vs 영업 **562,181,388** = **1.23배** → 정확한 상쇄가 아니다
- **재무제표는 계정별로 표시**된다. 총액이 우연히 맞아도 **재공품·제품 각 계정은 여전히 틀린다**
- 감사·세무에서 "상쇄되니 괜찮다"는 설명은 통하지 않는다
⟹ 채택 사유는 **①②③**이다. 나중에 재무제표용을 만들 때 이 근거가 그대로 재사용되지 않도록 명시해 둔다.

**단가 규칙**
```
생산창고 입고 단가 = 그 품목의 자재(MAT) 확정 스냅샷 avg_cost
                    없으면 pr_m_item_cost(cost_tag='1') 최신  ← 레거시와 동일 폴백
생산창고 자체의 이동평균을 (품목 × 재고위치) 축으로 전개
```
※ MAT avg_cost 는 월말값이므로 월중 입고에 쓰는 것은 **근사**다. 운영·관리용이라 허용하고,
   재무제표용을 만들 때 일단위 단가로 정밀화한다.

**대조 기준**: 레거시 생산재고는 확정 기말평가액이 없고 평가방법도 없다(12-6)
→ **금액 대조 불가. 수량 축으로만 diff0 한다.**

### 15-3. 적용한 최적화 3가지

**① 배치 INSERT (자재 58.4 → 3.7초, 15.7배)**
행 단위 `cur.execute` 로 넣어 **품목당 1회 왕복**이 발생했다(자재 2,441행 = 2,441왕복).
→ `pyodbc fast_executemany` + `executemany` 로 한 번에 전송. 공용 헬퍼 **`_snap_bulk()`** 신설,
   MAT·PRD·SAL 적재부를 모두 위임.

**② 원가엔진 싱글턴 + BOM 단가 (품목,연월) 캐시 (생산 21.4 → 6.8초)**
마감마다 `NxCostEngine()` 을 새로 만들어 내부 캐시(`_hasbom`/`_hdr`/단가)가 **매번 콜드**였고,
같은 품목을 일마감 31회 동안 31번 재전개했다.
→ 엔진 싱글턴(`_bom_engine()`, 죽으면 재생성) + `_BOM_PX_CACHE[(item, yymm)]`.

**③ 단가 체인 월 캐시 (생산 6.8 → 3.16초)**
`_prd_price` 가 마감마다 `PR_M_ITEM_COST` 전체 + 실매입 전표 as-of 누계 + `nx.item` 을 **전체 스캔**했다.
구성요소가 전부 월 단위로 사실상 불변이라 → `_PRD_PX_CACHE[yymm]`.

### 15-4. ★캐시 정합성 — 무효화 규칙
**자재 마감이 갱신되면 생산 단가 캐시는 낡는다.** `close_run` 에서 `domain='MAT'` 마감 직전에
`_PRD_PX_CACHE.clear()` · `_BOM_PX_CACHE.clear()` 로 무효화한다.
(생산 단가의 원천이 자재이므로 — §14-1)

**※근사 명시(의도적)**: 두 캐시 모두 **연월 단위**다. 월 내 단가 변동은 반영되지 않는다.
이 값들은 "다른 경로로 단가를 못 구한 품목"의 폴백이므로 월 단위로 충분하다고 판단했다.
**정밀이 필요해지면 캐시 키를 일자로 낮추면 된다**(코드 주석에도 명기).

### 15-5. 남은 성능 여지

- 월마감 재실행 64초 — 월 전체를 다시 전개하므로 일마감보다 느린 것이 정상.
