## 0. 한 줄 결론

**우리 신규 ERP의 계산용 BOM(`nx.bom_line`)은 "클린 3축 모델"이 아니라 레거시 CS를 새 테이블에 재현한 "미러"다.** 형태(테이블·품번통합)는 바꿨지만 의미(다중 플래그·변형SUB·죽은행)는 그대로 복제했다. 그래서 **신규 ERP인데도 레거시의 병(이중계상 등)이 그대로 나온다.**
그리고 **diff0은 "결과(원가·계획 수치) 동일"이지 "방식·구조 동일"이 아니다.** → 방식을 바꿔 클린으로 가도 되며, 조건은 오직 **오라클로 결과 동등성 증명**이다.

## 2. 구조적 진실 — "1 BOM 테이블 + 다중 독립 플래그"

한 개의 `nx.bom_line` 행이 **프로그램별로 다른 의미**를 갖는다(레거시 CS 그대로 복제):

```
cs_calc_except (원가용 제외)  ·  except_flag (소요/PR용 제외)
set_except (세트용)  ·  kitting (키팅용)  ·  sagub_default (사급용)
```

**실측 — 원가제외(cs_calc_except=1) 414행이 다른 축에선 살아있음:**

| 원가에선 제외지만… | 아직 쓰는 곳 |
|---|---|
| 소요(except_flag=0)엔 포함 | **312행** |
| 키팅 대상(kitting=1) | 189행 |
| 세트 포함(set_except=0) | 402행 |
| 사급(sagub_default=1) | 3행 |

➡️ **한 행이 "원가엔 빠지지만 소요/키팅/세트엔 쓰임" → 함부로 삭제 불가**(그 프로그램들이 깨짐). 레거시가 행을 안 지우고 플래그만 쌓은 이유 = 이 다중 용도. **이 오버로딩이 복잡함·지뢰의 근원.**

## 4. ★핵심 원칙 — diff0 = 결과 동일 ≠ 방식 동일

- 원가 오라클(`_harness/cost_oracle.py`, `SP_CS_견적서`)·계획 verify가 비교하는 건 **최종 숫자**(재료비 jae, 실원가 silwon, 계획 수량). **내부 BOM 구조·플래그는 안 본다.**
- 증명: MJC는 **삭제하든 플래그하든 원가 동일**. 방식이 달라도 결과 같으면 diff0.
- **오늘(현재일) 원가가 커 보이는 건 버그 아님** — nx 단가/LME 스냅샷이 당일치로 아직 안 올라온 **드리프트**. 검증은 **동기화된 과거 날짜(예 260630)** 로 해야 함. (검증 예: AJR77224002 260630 diff=0.14, 앵커 AJR75563503 정확일치.)

➡️ **함의: 레거시 플래그 구조를 흉내 낼 필요가 없었다.** 깨끗한 BOM으로 만들되 "결과가 같은지"만 오라클로 증명하면 diff0을 만족한다.

### 왜 그동안 미러로 만들었나
같은 방식 = 같은 결과가 **자동 보장**이라 빠르고 안전했기 때문(검증 부담 회피). 다른 방식은 **전 품목 결과 동등성 증명**이 필요. → 그 부채를 이제 갚으면 됨. (과거 "CS 강제정합→원가훼손→롤백" 이력도 같은 맥락.)

## 5. 클린 전환 원칙 (제자리 갈아엎기 금지)

**방식 자유 + 결과 고정**이므로:
1. **깨끗한 BOM을 "따로" 만든다** — 변형SUB→라우팅/조달, 죽은행 제거, 플래그 없음(= `unified_bom_schema.sql` 목표). 현재 미러는 **그대로 두고 병렬로.**
2. **오라클을 전 품목에 돌려 "클린 == 레거시 결과"를 증명.**
3. **전 품목 diff0 확인 후** 원가·계획 엔진을 클린 BOM 읽도록 **전환.** 라이브는 증명 끝날 때까지 안 건드림.
4. **끊는 시점 결정** = "이제 우리 엔진/ BOM이 정본이다"(diff0 게이트 해제)를 언제 선언할지. 그 전엔 diff0 유지.

### 클린 모델에서 다축 문제 해소
원가/소요/키팅/세트를 **축별로 분리**하면 한 행이 상충 플래그를 안 지므로, "안 쓰는 행 = 삭제"가 **깨끗하게 성립**(지금 미러에선 위험한 삭제가 클린에선 안전).

## 9. 클린전환 파일럿 대조 로그 (2026-08-24, AJR75563402)

**사용자 확정 모델(2026-08-24)**: "**LG BOM은 서브가 없다. 우리 BOM(nx.bom 클린)도 같은 구조로 했다. SUB는 R01(조달경로1)에서 넣은 것.**" → SUB(접미사 변형)는 실제 BOM 구조가 아니라 **조달경로(Sourcing 축)의 표현**이며, 레거시 미러는 그 route를 BOM 트리에 접미사 헤더로 복제해 넣었다.

### 9-1. 실측 구조 대조 (읽기전용, nx=PARTNER_ERP_TEST3)

**클린 `nx.bom` (parent_code=AJR75563402)** = **12개 평탄 자식, 전부 `is_lowest=Y`, SUB 없음.**
- 3A00375E·3H02717A·4930A20053B·4A00742C·5006AR4091C·5210A22409B·5410A30279K·MJU64794201/202/302(phantom·제작동관)·RAC30599301·RAC30599327

**미러 `nx.bom_header`** = AJR75563402가 **7개 헤더로 복제**(=메모리 "접미사 6변형"):
| bom_id | item_code | 성격 |
|---|---|---|
| 3998 | AJR75563402 | base |
| 1135 | -은납 | 조달경로(은납) |
| 4331 | -19-1 | 명진 Sub |
| 846 | -4-1 | 변형 |

### 9-2. 발견된 리프 차이 (route-specific, diff0 검증 대상)
클린(LG기반) vs 미러(레거시 CS) 리프가 **완전 일치하지 않음** — route에 따라 갈리는 지점:
- **5006AR4091C**(클린) vs **5006AR4091H**(미러 은납 route) — 접미 C/H 차이
- **RAC30599301 + RAC30599327**(클린 2개) vs **RAC30599301-1**(미러 1개) — 용접봉 코드 분해 차이
→ 이 차이가 **원가·소요에 영향 있는지**가 클린전환 diff0의 관건. (구조는 접히지만 리프 코드가 route마다 다름 = 클린 base+route 재구성이 각 변형의 레거시 결과를 재현해야 함.)

### 9-3. 검증 명제 (다음 단계)
> **클린 `nx.bom`(1헤더) + 조달경로 R01 적용 == 미러 각 변형(-은납/-19-1/…)이 내던 원가·소요와 diff0**
- 현 엔진(`NxCostEngine`)은 **미러 `bom_line`(bom_id)** 기준으로 원가 계산 → 미러 baseline은 즉시 산출 가능.
- 클린측 원가/소요 경로(nx.bom + route)가 **아직 없음** = 이걸 옆에 지어 미러와 대조(diff0 증명 후 repoint).
- 파일럿 백업 이미 존재: `nx.bom_header_bak_pilot_AJR30012009`·`nx.bom_line_bak_pilot_AJR30012009` (이전 세션 착수 흔적).

**상태**: 구조 대조 완료(위). 다음 = R01 조달경로 테이블 위치·매핑 확인 → 클린+route 원가/소요 재구성기 설계.

### 9-4. R01_REBUILD 대조 + ★드리프트 정황 (2026-08-24, 검증 필요)
정본 재독(`BOM_PROGRAM_MASTER`08-23·`BOM_STRUCTURE_CANON`·`R01_REBUILD_DESIGN`) 후 대조하니 **08-12 완료 상태와 현 DB가 어긋나는 정황 2건**:

### 9-5. ★교정 — "R01 드리프트"는 오진 (2026-08-24, 코드+사용자 확인)
9-4의 "R01 드리프트" 진단은 **틀렸음**. 실체:
