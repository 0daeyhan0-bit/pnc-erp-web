# 재생 파일럿 — 레거시 거래를 우리 프로그램으로 다시 입력하기

> 착수 2026-09-01. 대표 지시:
> "레거시에 입력된 거래 데이터를 신규 ERP 프로그램으로만 입력할 수 있을까? **단순 데이터 copy 가 아닌거야.**
>  그렇게 해서 우리 시스템이 동일한 결과를 낼 수 있는지 확인하고 싶다."
> "오늘 8시부터 30분 단위로" · "가장 많이 사용한 Assy 품번 10종으로 파일럿"
> "**꼭 프로그램을 사용해서 입력을 해야지 문제점들이 나올거야. 데이터만 밀어 넣지마.**"
> "그 재생기는 TEST BED 에 같이 넣는건 어때?"

---

## 1. 무엇을 하는가

레거시에 실제로 입력된 거래를 읽어, **우리 화면 API 를 HTTP 로 호출해서** 다시 입력한다.
직접 INSERT 는 하지 않는다 — 그러면 게이트·유효성·파생계산(원장·수불장·재고)을 전부 건너뛰어
**아무것도 검증되지 않는다.** 그게 "데이터 복사"와 "프로그램 입력"의 차이다.

| 파일 | 역할 |
|---|---|
| `_migration/replay_pilot.py` | 관측 — 30분마다 신규 거래를 유형별 집계(읽기 전용) |
| `_migration/replay_cases.py` | 레거시 거래 → TestBed 케이스(dict) 변환. **DB 쓰기 없음** |
| `_migration/flow_cases.py` | 훅 1개 — `REPLAY_YMD` 있을 때만 케이스를 덧붙임(평소 무영향) |
| `_migration/flow_server.py` | 롤백 서버(commit 무력화) — 실제 API 가 돌지만 DB 확정 안 됨 = **오염 0** |

대상 10종(2026-08-31 실측, 생산+출하 거래건수 상위 완제품):
`MJU63357501 · AJJ75838625 · AJR73965506 · AJR73965505 · AJR73965606 · AJR73965607 ·
 AJR30004702 · AJR30077403 · AJR76582506 · AJR76582505`

이 10종의 어제 거래 = 생산 47 · 완성이동 157 · 키팅 383 · 자재수불 114 · 생산자재 97 · 가공세트 16.

## 2. 첫 실행 결과 (2026-09-01 05:3x · 어제 거래 5건)

```
PASS 13 · FAIL 5 · SKIP 1   ← FAIL 5 = 재생분 전부
오염 0 PASS — 기동시점 행수와 불변
```

**파이프라인은 작동한다.** 레거시 거래가 케이스로 변환되고, 하네스가 실제 API 를 호출하고,
결과가 probe/delta 로 판정되고, 롤백으로 오염 0 이 증명됐다.

재생 5건은 **전부 재고 게이트에 거부(400)** 됐다:

```
재생 생산실적 AJR30077403 x200
  → 자재부족으로 생산실적 등록 불가 — 3A00375A: 소요 200 > 가용 155
     (준비재고 0 + 자재재고 155[자재정본]) · 생산창고에 5 있으나 백플러시 소비축이 아님
재생 생산실적 AJR30004702 x10
  → MJU00697402: 소요 10 > 가용 2 ; MJU00697501: 소요 70 > 가용 49
```

### ★이건 결함이 아니다 — 재생 시점의 문제다

어제 거래를 **오늘** 재생했기 때문이다.
어제 거래는 오늘 새벽 매일 마이그(`r_delta_sync`)로 nx 에 이미 반영됐고, **자재도 이미 차감됐다.**
그 상태에서 같은 생산을 또 넣으니 "자재가 없다" 가 맞는 답이다.

⟹ **대표 구상("오늘 8시부터 30분 단위")이 정확히 옳다.**
   매일 마이그는 **아침 7:30 에만** 돈다. 즉 업무 중 레거시에 쌓이는 거래는 **nx 에 아직 없다.**
   그 구간에서 재생하면 재고 기준선이 레거시와 같아 정합이 맞는다.
   ※단, 이 가정은 오늘 실제로 돌려봐야 확인된다(§4).

### 부수 확인 — 게이트 메시지가 쓸 만하다

거부 사유가 품목·소요·가용·축까지 짚어준다
("생산창고에 5 있으나 백플러시 소비축이 아님"). 진단에 그대로 쓸 수 있다.
재고 게이트 하드룰(예외 금지·차단 시 사유 고지)이 실제로 지켜지고 있음이 재생으로 재확인됐다.

## 3. 운영 방법 (30분 사이클)

```
# 시작할 때 한 번 — 지금까지를 '이미 본 것' 으로 표시
python _migration/replay_pilot.py --baseline

# 30분마다 — 신규 거래 관측(읽기 전용)
python _migration/replay_pilot.py --observe

# 누적 기준값(우리 재생 결과와 맞춰볼 숫자)
python _migration/replay_pilot.py --summary

# 재생 — 반드시 롤백 서버에 대고
python _migration/flow_server.py --port 8099          (다른 창)
set REPLAY_YMD=<YYMMDD>
python _migration/flow_scenarios.py --port 8099 --kind F
```

`REPLAY_LIMIT=N` 으로 건수를 제한한다(처음엔 작게).

## 4. ☐ 남은 것

1. **오늘 8시 이후 실측** — 마이그 전 구간에서 재생하면 게이트를 통과하는지. §2 의 가정 검증.
2. **순서 재생** — 지금은 생산실적만 넣는다. 실제로는 자재입고 → 키팅 → 생산 → 출하 순서가 있다.
   시간순(`PROD_HMS`·`INSERT_DATETIME`)으로 전 유형을 섞어 넣어야 종단 흐름이 재현된다.
3. **유형 확대** — 키팅 `/api/kitting/cell-confirm` · 출하 `/api/lgsale/save` · 자재수불 `/api/stock/save`.
4. **결과 대조기** — 재생 후 품번별 수량·금액·재고 증감을 레거시와 대조.
   ★키(MAINT_SEQ)로 비교하면 안 된다 — 우리가 채번하므로 번호가 다르다. **집계 축으로만** 비교한다.
