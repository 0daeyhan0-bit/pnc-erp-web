# 재생 파일럿 — 레거시 거래를 우리 프로그램으로 다시 입력하기

> 착수 2026-09-01. 대표 지시:
> "레거시에 입력된 거래 데이터를 신규 ERP 프로그램으로만 입력할 수 있을까? **단순 데이터 copy 가 아닌거야.**
>  그렇게 해서 우리 시스템이 동일한 결과를 낼 수 있는지 확인하고 싶다."
> "오늘 8시부터 30분 단위로" · "가장 많이 사용한 Assy 품번 10종으로 파일럿"
> "**꼭 프로그램을 사용해서 입력을 해야지 문제점들이 나올거야. 데이터만 밀어 넣지마.**"
> "그 재생기는 TEST BED 에 같이 넣는건 어때?"

---

## 1. 무엇을 하는가

레거시에 실제로 입력된 거래를 읽어, **우리 화면 API 를 HTTP 로 호출해서** 다시 입력한다.
직접 INSERT 는 하지 않는다 — 그러면 게이트·유효성·파생계산(원장·수불장·재고)을 전부 건너뛰어
**아무것도 검증되지 않는다.** 그게 "데이터 복사"와 "프로그램 입력"의 차이다.

| 파일 | 역할 |
|---|---|
| `_migration/replay_pilot.py` | 관측 — 30분마다 신규 거래를 유형별 집계(읽기 전용) |
| `_migration/replay_cases.py` | 레거시 거래 → TestBed 케이스(dict) 변환. **DB 쓰기 없음** |
| `_migration/flow_cases.py` | 훅 1개 — `REPLAY_YMD` 있을 때만 케이스를 덧붙임(평소 무영향) |
| `_migration/flow_server.py` | 롤백 서버(commit 무력화) — 실제 API 가 돌지만 DB 확정 안 됨 = **오염 0** |

대상 10종(2026-08-31 실측, 생산+출하 거래건수 상위 완제품):
`MJU63357501 · AJJ75838625 · AJR73965506 · AJR73965505 · AJR73965606 · AJR73965607 ·
 AJR30004702 · AJR30077403 · AJR76582506 · AJR76582505`

이 10종의 어제 거래 = 생산 47 · 완성이동 157 · 키팅 383 · 자재수불 114 · 생산자재 97 · 가공세트 16.

## 2. 첫 실행 결과 (2026-09-01 05:3x · 어제 거래 5건)

```
PASS 13 · FAIL 5 · SKIP 1   ← FAIL 5 = 재생분 전부
오염 0 PASS — 기동시점 행수와 불변
```

**파이프라인은 작동한다.** 레거시 거래가 케이스로 변환되고, 하네스가 실제 API 를 호출하고,
결과가 probe/delta 로 판정되고, 롤백으로 오염 0 이 증명됐다.

재생 5건은 **전부 재고 게이트에 거부(400)** 됐다:

```
재생 생산실적 AJR30077403 x200
  → 자재부족으로 생산실적 등록 불가 — 3A00375A: 소요 200 > 가용 155
     (준비재고 0 + 자재재고 155[자재정본]) · 생산창고에 5 있으나 백플러시 소비축이 아님
재생 생산실적 AJR30004702 x10
  → MJU00697402: 소요 10 > 가용 2 ; MJU00697501: 소요 70 > 가용 49
```

### ★이건 결함이 아니다 — 재생 시점의 문제다

어제 거래를 **오늘** 재생했기 때문이다.
어제 거래는 오늘 새벽 매일 마이그(`r_delta_sync`)로 nx 에 이미 반영됐고, **자재도 이미 차감됐다.**
그 상태에서 같은 생산을 또 넣으니 "자재가 없다" 가 맞는 답이다.

⟹ **대표 구상("오늘 8시부터 30분 단위")이 정확히 옳다.**
   매일 마이그는 **아침 7:30 에만** 돈다. 즉 업무 중 레거시에 쌓이는 거래는 **nx 에 아직 없다.**
   그 구간에서 재생하면 재고 기준선이 레거시와 같아 정합이 맞는다.
   ※단, 이 가정은 오늘 실제로 돌려봐야 확인된다(§4).

### 부수 확인 — 게이트 메시지가 쓸 만하다

거부 사유가 품목·소요·가용·축까지 짚어준다
("생산창고에 5 있으나 백플러시 소비축이 아님"). 진단에 그대로 쓸 수 있다.
재고 게이트 하드룰(예외 금지·차단 시 사유 고지)이 실제로 지켜지고 있음이 재생으로 재확인됐다.

## 5. ★★★가장 중요한 발견 — 레거시 거래의 절반은 '입력'이 아니다 (2026-09-01)

재생 대상을 넓히다가 키팅이 **취소 374 vs 확인 9** 로 나왔다. 실제 업무가 취소 위주일 리 없다.
`INSERT_WINDOW`(레거시 화면명)로 갈라 보니 거래가 **두 종류**였다.

| | 무엇 | 재생 |
|---|---|---|
| ① 사람이 화면에서 입력 | 자재입고 `tag 9·C` · 키팅 `tag 1·2` · 생산실적 · 출하 `tag J` | **대상** |
| ② 그 입력 때문에 시스템이 자동 생성 | 자재 `tag B` 2,091 · 준비 `tag A` 1,035 · 완성 `tag P` 203 · 생산자재 `tag 4` 1,357 | **금지** |

실측(260831 전체):
```
[준비 PU_T_READY_STOCK_MAINT]
  tag 1  w_pr_input_460_new  384행  +8,325   키팅 확인          → ①
  tag 2  w_pr_input_460_new   73행    -891   키팅 취소          → ①
  tag A  w_pr_input_520/260 1,035행 -14,760  준비재고 소진(생산 부산물) → ②
[자재 PU_T_STOCK_MAINT]
  tag 9  w_pu_stock_057      75행 +194,370  발주입고            → ①
  tag C  w_pu_stock_057_2   119행   +4,281  자재개별일괄입고     → ①
  tag B  w_pr_input_460_new 2,091행 -75,975 키팅 화면의 자동 자재차감 → ②
[완성 SA_T_STOCK_MAINT]
  tag J  w_pr_input_040     420행  -59,118  출하등록            → ①
  tag P  w_pr_input_260/520 203행   +8,180  생산입고            → ②
```

**②를 재생하면 이중계상이 된다.** 우리 시스템도 ①을 받으면 ②를 스스로 만들기 때문이다.
⟹ **②는 입력이 아니라 채점 기준이다.**
  "우리가 ①을 넣었을 때 ②에 해당하는 값이 나오는가" — 이게 이 파일럿의 진짜 질문이다.

※이 구분을 못 했으면 재생 결과가 전부 2배로 나왔을 것이고,
  그 틀린 숫자를 보고 **우리 프로그램이 잘못됐다고 결론 냈을 것**이다.

### 반영 결과 (260831 · 10종)
```
재생 케이스 202건 = 생산 47 + 출하 146 + 키팅 9(확인8·취소1)
파생 제외   487건 (자재 113 + 준비 374)  ← 재생 금지, 채점 기준
스킵          1건 (tag S — 세트 계열, 매핑 미확정)
```

### ☐ 한계 — 자재입고는 품번 축으로 안 잡힌다
10종은 **완제품**이라 그 품번으로는 자재입고(`tag 9`)가 0건이다.
자재는 하위 품번(`MJU00697402` 등)이고 `PU_T_STOCK_MAINT` 는 `ITEM_CODE`(상위품)/`MAT_CODE`(자재)가 따로다.
자재입고까지 재생하려면 **10종의 BOM 자재를 역으로 구해** 대상에 넣어야 한다.

## 6. ★실증 — 마이그 이후 구간이면 통과한다 (2026-09-01 08:05)

§2 에서 세운 가정("어제 것을 오늘 재생하면 막히는 게 맞다. 마이그 전 구간이면 통과할 것이다")을
**오늘 실제 거래로 확인했다.**

```
REPLAY_YMD=260901  REPLAY_SINCE='2026-09-01 07:30:00'  REPLAY_LIMIT=20
결과: PASS 32 · FAIL 0 · SKIP 1
  재생②키팅 AJR30133601 +1   → 원장RDY +1   ✅
  재생②키팅 AJR30078601 +25  → 원장RDY +25  ✅   (18건 전부 통과)
```

| | 어제 거래를 오늘 재생 | 오늘 거래를 마이그 후 재생 |
|---|---|---|
| 결과 | **5건 전부 거부**(자재부족) | **18건 전부 통과** |
| 이유 | nx 에 이미 반영돼 자재가 차감된 상태 | nx 에 없는 구간 = 재고 기준선이 맞음 |

⟹ **재생은 '마이그 이후 ~ 지금' 구간에서만 유효하다.** 대표 구상(30분 단위)이 이 조건을 만족한다.

### 오염 0 — 독립 커넥션으로 직접 확인
거래·재고·원장 12개 테이블 중 **11개가 정확히 ±0**.
`nx.app_session` 만 +3 인데 이는 **하네스 로그인 세션**이다(재고·거래 데이터 아님).
☐ 다만 `flow_server.ROLLBACK_TABS` 에 들어 있는데도 롤백되지 않았다 —
  로그인 경로가 몽키패치된 공유 커넥션을 타지 않는다는 뜻. TestBed 한계로 등록.

### ☐ 총합 대조는 아직 못 쓴다
이번 실행의 총합 대조는 전부 '차이' 로 나왔는데 **대조기 결함이 아니라 실행 조건 탓**이다:
  · `REPLAY_LIMIT=20` 으로 잘랐으니 레거시 총합과 맞을 수가 없다
  · 기존 TestBed 기본 케이스(자재입고 +100 · 생산 +7 등)가 같은 프로브에 섞였다
    (실측: 우리 원장MAT +100 = 기본 케이스의 자재입고, 공정실적 +7 = 기본 케이스)
⟹ 총합 대조를 쓰려면 **재생 케이스만 · 전량** 돌려야 한다. `--only 재생` 지원이 필요하다.

## 7. ★★★컷오버 차단급 발견 — 준비재고 기초가 비어 있다 (2026-09-01 09:35)

재생 케이스만 전량(`--only 재생`) 돌린 결과: **PASS 19 · FAIL 7 · 오염 0**.
**FAIL 7 은 전부 생산실적**이고 사유가 하나로 모인다.

```
재생③생산 AJR73965505 x12
  → 자재부족으로 생산실적 등록 불가
     MJU62916207: 소요 12 > 가용 7 (준비재고 0 + 자재재고 7[자재정본])
                  · 생산창고에 300 있으나 백플러시 소비축이 아님
```

**준비재고가 항상 0** 이다. 왜인지 코드로 확인했다(`backflush._avail_bulk`):

| 축 | 게이트가 읽는 곳 | 기초가 있나 |
|---|---|---|
| MAT 자재 | 실시간 자재정본 + `nx.PU_T_MAT_STOCK_WH`(미러 폴백) | **있다** (그래서 값이 나온다) |
| **RDY 준비** | **`nx.stock_ledger` STOCK_POINT='RDY' 뿐** | **없다** |

실측:
```
우리 nx.stock_ledger RDY        :      19행  합계    308
레거시 PU_T_READY_STOCK_MAINT   : 942,153행  합계 -1,585,847
```

### 무슨 뜻인가
레거시 거래는 **미러 테이블로만** 동기화되고 **우리 단일원장에는 들어오지 않는다.**
자재는 미러 폴백이 있어 값이 보이지만, **준비재고는 우리 원장이 유일 소스**라 0 으로 읽힌다.
⟹ **컷오버하면 모든 생산실적이 자재부족으로 막힌다.**
  이건 우리 프로그램의 버그가 아니라 **기초 재고가 안 심어진 것**이다.

### 이미 등록돼 있던 과제였다
`CUTOVER_MUST_AND_DAILY_MIGRATION.md §B-2 7번`
  "기초 스냅샷 심기 — 각 재고점 기초를 nx.stock_close_snap 에 적재"
**이 파일럿이 그 과제의 무게를 실측으로 보여줬다** — 미착수가 아니라 **컷오버 차단 사유**다.

### ☐ 결정이 필요한 갈림길
1. **준비재고도 실시간 엔진으로** — 자재처럼 레거시 미러(`PU_T_READY_STOCK_MAINT`)를 fold.
   컷오버 전 병행운영에는 이게 맞다. 단 컷오버 후엔 미러가 죽으므로 임시책이다.
2. **기초 스냅샷 심기** — 컷오버 시점 준비재고를 우리 원장 기초로 1회 적재.
   §B-2 7번 그대로. 컷오버 후에도 유효한 정공법.
⟹ 둘 다 필요해 보인다(1=지금 검증을 위해, 2=컷오버를 위해). **대표 판단 필요.**

### 부수 확인 — 키팅이 자재를 차감하지 않는다(설계 차이, 결함 아님)
총합 대조에서 `원장MAT` 레거시 −4,536 vs 우리 0.
레거시는 키팅 화면이 자재를 함께 차감한다(`tag B`). 우리는 **백플러시에서만 차감**한다
([[newerp-kitting-redesign]] flag-only 설계). 축이 다른 것이지 틀린 것이 아니다.
⟹ 총합 대조표에 **설계 차이 축**을 따로 표시해야 한다(안 그러면 매번 '차이' 로 읽힌다).

| 3H01582D | 0 | 0 | 0 |
| MJU00745109 | 0 | 0 | 0 |

**레거시에도 준비재고가 0 이었다.** 기초를 심었어도 이 7건은 똑같이 막혔다.

### 진짜 원인은 둘이고, 서로 다르다

**① 생산창고를 소비축에서 뺀 설계 (1종)**
`MJU62916207` 은 생산창고에 **260** 이 있다. 우리 `_avail_bulk` 는 그 값을 읽어 두고도
가용에 더하지 않는다(`prd_wh` 로 따로 담아 메시지에만 쓴다 — "생산창고에 300 있으나
백플러시 소비축이 아님"). 레거시는 그걸 쓴다. **설계 차이다.** 어느 쪽이 맞는지는 판단이 필요하다.

**② 레거시가 재고 없이 생산을 등록한다 (4종)**
나머지 4종은 **레거시에도 어느 창고에도 재고가 0** 인데 생산실적이 등록돼 있다.
레거시에 재고 게이트가 없기 때문이다(정본 §B-2 4-a "레거시가 게이트 없이 쌓아둔 현존 마이너스 재고").
⟹ **이 4건은 우리가 막는 게 맞다.** 재생 FAIL 이 아니라 **우리 게이트가 레거시의 마이너스 재고 관행을
  차단하고 있다는 증거**다. 개선이지 결함이 아니다.

### 준비재고 기초는 어떻게 되나
기초가 비어 있는 것 자체는 사실이다(우리 원장 RDY 19행 vs 레거시 잔량 테이블 3,124행).
다만 **이번 FAIL 의 원인이 아니므로 "컷오버 차단 사유" 승격은 근거가 약했다** → 되돌린다.
별개 과제로 남긴다. 참고로 레거시 `PU_T_READY_STOCK` 합계는 **−124,986**(음수 다수)이라
**그대로 심으면 안 된다** — 심기 전에 §B-2 4-a(마이너스 정리)가 선행돼야 한다.

### 교훈
거부 메시지의 첫 항목('준비재고 0')을 보고 원인이라 단정했다.
**막힌 쪽만 보고 원천(레거시)을 안 봤다.** 같은 데이터를 양쪽에서 봐야 했다.

## 9. 판정 관점을 바로잡다 — "프로그램이 정상 작동하는가" (2026-09-01 10:26)

> 대표: "지금 우리가 테스트를 하려고 하는거잖아. **프로그램이 정상적으로 작동을 하는지.**
>        그 관점에서 접근을 했으면 좋겠어."

§7~§8 에서 나는 재고부족 거부(400)를 **FAIL 로 세고** 있었다. 그래서 결과가
"우리 프로그램이 레거시와 다르다" 처럼 읽혔고, 급기야 **게이트 설계를 바꿀지 묻는 데까지** 갔다.
틀린 접근이다. **재고가 없어 막는 것은 게이트가 제 일을 한 것 = 정상 작동**이다.

### 판정 기준 (`allow_reject`)
| 응답 | 판정 | 이유 |
|---|---|---|
| 200 + 기대 delta | PASS | 값이 제대로 적혔다 |
| **4xx 거부 + DB 무기록** | **PASS** | 프로그램이 판단해서 막았다. 사유를 기록한다 |
| 4xx 거부 **+ DB 기록** | FAIL | 막았다면서 쓴 것 = 진짜 결함 |
| 5xx · 연결실패 | FAIL | 터진 것 |
기존 케이스는 `allow_reject` 가 없으므로 **동작이 그대로다**(회귀 없음).

### 결과 — PASS 54 · FAIL 0 · 오염 0
```
재생②키팅 AJR30077403 +200   → 원장RDY +200                    ✅ 값이 적혔다
재생③생산 AJR73965505 x12    → 정상 거부(400)·무기록            ✅ 게이트가 막았다
     사유: MJU62916207 소요 12 > 가용 7 (준비 0 + 자재 7)
           · 생산창고에 300 있으나 백플러시 소비축이 아님
재생④출하                    → 원장ASY −196                     ✅
```
**500·예외·크래시 0 · 거부하면서 DB 에 쓴 것 0 · 재고/거래 테이블 오염 0.**
⟹ **오늘 재생이 답한 것: 우리 프로그램은 정상 작동한다.**

### 거부 사유는 '결함 목록' 이 아니라 '차이 목록' 이다
막힌 건들의 사유는 두 갈래이고, 둘 다 이미 정본에 등록된 항목이다.
  · 생산창고를 소비축에서 뺀 설계 → 판단 대기(§8 ①)
  · 레거시가 재고 없이 생산 등록 → 우리가 막는 게 맞다(§8 ② · §B-2 4-a)
**지금 고칠 것이 아니라 알고 있어야 할 것**이다.

### ☐ 총합 대조는 이 관점에선 부차적
생산이 (정상적으로) 거부되면 파생이 안 생기므로 총합은 당연히 안 맞는다.
총합 대조는 "레거시와 같은 값인가" 를 볼 때 쓰는 도구이고, 그건 **재고 기준선을 맞춘 뒤**에야 의미가 있다.
