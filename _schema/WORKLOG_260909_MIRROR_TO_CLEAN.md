## 0. 왜 하는가

**컷오버 후에는 미러가 얼어붙는다**(CLAUDE.md §1-9-1). 레거시가 은퇴하면 미러를 갱신할
주체가 사라지고, 코드는 **옛 값을 조용히 계속 읽는다**. 그게 최악이다.

오늘 실제로 그 증상을 두 개 확인했다:

- **달력** — 클린은 2026-07-23 미러 복사본에서 멈춰 있었고, 8/20 에 조상협님이 레거시에서
  지정한 휴무 2건(8/17·8/28)과 파트 휴무 12건이 웹에 없었다. 그런데 코드는 미러를 읽고
  있어서 **화면에서 달력을 고쳐도 편성·키팅·가공에 반영되지 않았다.**
- **파트마스터** — 웹이 미러에 `ALTER TABLE` 로 얹은 컬럼(`BARCODE_FLAG`·`PROD_RESULT_TYPE`)이
  미러 재적재 때 **값째로 날아갔다**(8/30 에 이어 두 번째). 대표님이 다시 설정하셨다.

## 1. 달력 3종

### 1-1. 순서가 중요했다 — 데이터 먼저, 코드 나중

코드부터 바꿨다면 **7월 값으로 되돌아갔다.** 클린이 낡은 스냅샷이었기 때문이다.

```
① sync_calendar_260909.py --apply     클린을 최신화 (14건)
     근무달력 값갱신 2건   (8/17·8/28 — 레거시에서 휴무 지정)
     공장운영달력 신규 12건 (7/31·8/17·8/26)
     라인달력 결손 0 · 불일치 0
② make_calendar_views_260909.py       호환뷰 3종
③ switch_calendar_to_clean_260909.py  코드 22곳
```

### 1-2. 호환 뷰를 쓴 이유

컬럼명·형식이 달라 단순 치환이 안 된다.

```
미러  CALENDAR_YYMD(char8 'YYYYMMDD') · WORK_TEAM · TIME_TYPE · WORK_STATS
클린  cal_ymd(date)                   · team      · (없음)    · work_stats
```

미러 모양 그대로 노출하는 뷰를 두면 `WHERE`·`SUBSTRING` 을 그대로 둘 수 있어
변경이 **테이블명 한 단어**로 끝나고 되돌리기도 쉽다.

```
nx.v_cal_work ← work_calendar   (HR_M_CALENDAR 모양)
nx.v_cal_line ← line_calendar   (PR_M_LINE_CALENDAR 모양)
nx.v_cal_part ← part_calendar   (PR_M_PART_CALENDAR 모양)
```

### 1-3. ★웹 입력분 보호

`line_calendar.src` 가 `LG`(엑셀 업로드 631행)·`MANUAL`(화면 수기 2행)인 행은
미러로 덮으면 안 된다. 동기화 대상은 `src='MIRROR'` 뿐.

### 1-4. ★두 달력은 중복이 아니다 (대표 확인)

`line_calendar` 의 `line_no='공통'`(3,926행)과 `work_calendar`(5,264행)가 겹치고
**697일 값이 다르다**. 통합하려 했으나 대표님이 바로잡아 주셨다 —

> "적용 기준이 달라서 서로 다른 거야. **라인은 고객사, 근무는 사내 기준 달력**"

실측 예: 2026-09-24·25 는 근무달력=4(휴무) / 라인공통=1(정상). 사내는 쉬는데 고객사 라인은 돈다.
**통합했다면 사내 기준으로 고객사 달력을 덮어써 당김일자가 통째로 틀어졌을 것.**

### 1-5. 공장운영 달력관리 탭 숨김

`cal_part` 탭은 **안정화 뒤 구축예정**(대표 지시). 화면·API·데이터(360행)는 그대로 두고
`screens.base.js` 의 TABS 배열에서만 뺐다. 되살릴 한 줄을 주석으로 남겼다.
편성은 파트달력을 계속 읽는다.

**② 이중 접두어.** `{S}.PR_M_ITEM_PROC_GAGONG` → `{S}.nx.v_item_proc` 가 되어 8곳이 깨졌다.
변수 스키마(`{S}`·`{SCH}`)를 쓰는 곳은 치환 후 반드시 점검할 것.

## 6-2. 파트마스터 (PR_M_PROC_GAGONG) — 80곳 + SP 22곳

### 왜 이게 가장 급했나 — **같은 사고를 두 번 겪은 곳**

웹이 미러에 `ALTER TABLE` 로 얹은 컬럼이 레거시 재적재 때 날아간다.

```
BARCODE_FLAG      '1'=바코드실적 허용
PROD_RESULT_TYPE  ''미지정 / 'R'준비재고 / 'W'자재창고출고
```

| 시점 | 증상 |
|---|---|
| 2026-08-30 | **컬럼 자체 소실** → 파트마스터 "백엔드 연결 실패", 드래그 실적 전면 불가 |
| 2026-09-09 | **값 전멸(NULL)** → 대표님이 S8·S10 준비재고를 다시 설정 |

방어로 넣었던 `_ensure_result_cols()`(조회·저장 진입마다 `ALTER` 재시도)는
**컬럼만 되살릴 뿐 값은 복구하지 못한다.** 근본 해결은 클린 이전뿐이라 옮겼다.

### 데이터는 그대로다 (대표 확인)

> "PR_M_PROC_GAGONG 은 이데이터 그대로 쓰면 되는거 아니야?"

맞다. 새 값을 만들 일이 없었다 — 라이브 23행 = 미러 23행, **웹 신규등록 0**.

```
seed_part_master_260909.py --apply
  nx.part_master 신설 · 23행 씨딩 · 호환뷰 nx.v_part_master
  결손 0 · 값불일치 0 → 커밋
  ★S8 08라인(서포터) → 준비재고 / S10 10라인(자동은납) → 준비재고  (보존 확인)
```

컬럼은 미러 18개 중 **코드가 실제 읽는 14개**만 옮겼다.
버린 것 = `MIX_GAGONG`·`UPDATE_IP/COMPUTER/WINDOW`(참조 0곳).

### 조회는 뷰, 쓰기는 실테이블

```
조회 80곳 → nx.v_part_master   (미러 컬럼명 그대로 노출 → SQL 무수정)
쓰기  4곳 → nx.part_master     (partmaster.py — 유일한 쓰기 화면)
```

`partmaster.py` 는 컬럼명이 소문자로 바뀌므로 뷰로 대신할 수 없어 **수동 편집**했고,
`_ensure_result_cols()` 는 **삭제**했다. 클린은 재적재 대상이 아니라 방어가 필요 없다.

### 치환 분류 — 어제 함정이 그대로 재현됐다

| 형태 | 예 | 처리 |
|---|---|---|
| 3부 이름 | `PARTNER_ERP_TEST3.nx.PR_M_PROC_GAGONG` | 테이블명만 교체 |

## 6-3. 파트별 작업자 (PR_M_PROC_GAGONG_WORKER) — 6곳 + SP 1곳

### ★함정이 재현됐다 — "같은 줄에 SQL 키워드" 판정은 부족하다

어제 쓴 규칙(같은 줄에 `FROM|JOIN|EXISTS…` 가 있으면 실제 쿼리)이
**docstring 을 치환 대상으로 잡았다**:

```
gongsu.py:143  """… 해당일 이미 등록된 (파트,작업자)는 exists=True 로 표시."""
                                                        ~~~~~~ ← EXISTS 로 오인
```

⟹ 판정을 **"키워드가 테이블명 바로 앞에 있어야 한다"** 로 바꿨다.
`\b(FROM|JOIN|INTO|UPDATE|DELETE FROM|TABLE)\s+[\w.{}\[\]]*<테이블>\b`
이후 보존 2곳(gongsu:143 · prodsheet:1053)이 정확히 걸러졌다.

### ★검증 중 내가 데이터를 바꿨다 (복구 완료)

"현재 명단을 그대로 저장하면 변화 0" 이라고 가정하고 검증했는데,
`S1 신선영 반장`(플래그 `''`)이 `'0'` 으로 바뀌었다. **두 번** 냈고 두 번 복구했다.

검증 = 빈 플래그가 없는 파트(S10, 2명 전부 '1')로 변경

그리고 **검증을 과하게 잡아 오래 걸렸다**(대표님 지적 "너무 오래 걸리는데").

## 6-6. ★잔존 마무리 — "잔존 0" 보고가 부실했다

대표님 질문("그럼 모두 정리 된거야?")에 답하려 **전수 재점검**을 돌리니 6종에 잔존이 있었다.
각 건마다 "잔존 0" 이라고 보고했는데, **그건 그때 그 테이블만, 그 방식으로만 본 것**이었다.

### 무엇을 빠뜨렸나

| 빠뜨린 것 | 실제로 남아 있던 곳 |
|---|---|
| **스칼라 함수(`f_*`)** — SP(`P` 타입)만 훑고 함수를 안 봤다 | 달력 3종이 **당김일자 계산 함수**에 11곳 |
| **딕셔너리 `"t":` 값** — 앞에 SQL 키워드가 없어 정규식이 못 잡음 | `basemaster.py` 달력 3종 |

| **웹이 간접 호출하는 함수** — SP 가 부르는 함수까지 안 따라감 | `f_reld_doosung_live` · `f_st_part_day_live` 등 |

### ★그러다 더 큰 것을 찾았다 — 함수가 **낡은 달력**을 읽고 있었다

함수가 `dbo` 스키마에 있으므로 실제 해석은 **`PARTNER_ERP_TEST3.dbo.HR_M_CALENDAR`** —
`nx` 미러가 아니라 **또 다른 사본**이었다. 그리고 그게 낡았다:

아무도 눈치채지 못했다. §6-1 에서 "달력을 고쳤다"고 했지만 **함수에는 그대로 남아 있었다.**

### ★검증 기준을 두 번 잘못 잡았다 (대표 확인으로 교정)

처음엔 **"값이 변하면 안 된다"**로 판정해 두 번 롤백했다.
대표님이 **"레거시하고 똑같이 맞추면 변동 없을꺼야"** 라고 짚어 기준을 바꿨다 —

## 6-7. 가공바코드 실적처리 하위자재 BOM (PR_M_ITEM_BOM) — 1곳

대표님 지시. 가공생산진척관리(전표발행)의 **가공바코드실적처리** 모달이

### 발견 경위 — 실적처리는 재고를 5갈래로 움직인다

## 6-8. 품목/자재 조회 (`/api/item/list`) — 자기조인 · 거래처명 · 빈 품번 행

대표 지시 **"nx.item 으로 해야지"**. 화면 부제가 `라이브 · 레거시 w_pr_master_010`
이고 외경·두께가 전부 0 이라 미러를 읽는 줄 알았는데, **품목 소스는 이미 `nx.item` 이었다.**
실제 결함은 그 주변 셋이었다.

### ★먼저 — 0 으로 보인 건 결함이 아니었다

캡처된 품목(`6s CAP`·`9 CAP`·`12S CAP` …)은 전부 **소분류 230 = 부자재/소모품**이다.
파이프가 아니니 외경·두께가 원래 없다. **데이터가 실제로 0** 이었다.
`nx.item` 전체로 보면 외경 11,093 · 두께 11,052 · 단중 9,955 건이 정상적으로 들어 있다.

⟹ **화면에 0 이 보인다고 소스를 의심하기 전에 그 행이 무슨 품목인지부터 볼 것.**

### ① 자기조인 — 과거 전환의 흔적

```sql
FROM PARTNER_ERP_TEST3.nx.item i
LEFT JOIN PARTNER_ERP_TEST3.nx.item nx ON nx.item_code = i.ITEM_CODE COLLATE DATABASE_DEFAULT
```

원래 `PR_M_ITEM i LEFT JOIN nx.item nx` 였다. 전환 때 **`i` 쪽만 치환**해서
같은 테이블을 두 번 읽는 모양이 됐다. `COLLATE DATABASE_DEFAULT` 도 그 시절 잔재다.
결과는 맞았지만 얻는 것 없이 비용만 냈다. 단일 참조로 정리.

⟹ **미러→클린 치환 후에는 조인 상대편도 봐야 한다.** 한쪽만 바꾸면 자기조인이 남는다.

### ② 거래처명이 미러였다

`nx.CM_M_CUST` → **`nx.partner`**. 컷오버에 죽는 경로였다(§1-9-1).
`ISNULL(clean, mirror)` 같은 폴백은 넣지 않았다 — 없으면 코드가 그대로 보이게 둔다.

### ③ 라이브 커넥션으로 nx 를 크로스DB 참조

`_conn()`(라이브 RO)으로 `PARTNER_ERP_TEST3.nx.*` 를 3-part 이름으로 읽고 있었다.
읽는 게 전부 nx 였으므로 `_nx()` 로 바꾸고 3-part 이름을 제거했다.

같이 걸린 것 — **`price.py` 에 로컬 `_kindmap` 이 있어 `common._kindmap` 을 가리고 있었다.**
로컬 판은 `_KINDMAP_EXT`(우리 소유 코드 240 용접봉 등)를 얹지 않아
자재조회에서 **240 라벨이 코드로 보였다**. common 판으로 위임해 해소.

⟹ **같은 이름의 로컬 헬퍼가 공용 헬퍼를 가리고 있는지 확인할 것.** 조용히 기능이 빠진다.

### ④ 빈 품번 행

`ITEM_CODE=''` 인 행 1건이 정렬상 **조회 첫 줄**에 나왔다(화면 캡처의 맨 위 빈 행).
`WHERE` 에서 제외.

### ★데이터 결손도 함께 — 코드 폴백이 아니라 데이터로

매입처칸에 이름 대신 코드가 뜨는 품목이 있었다. 원인은 **클린 `nx.partner` 결손**이었다.

```

  2370 (주)승호산업 · 2371 원광산업 · 2372 Huayi(Sungwon) · 2373 (주)청송에어팩
```

`partner_type` 이 NOT NULL 이라 값이 필요했는데, **추측하지 않고 기존 357행에서 역산**했다.

|---|---|---|
| 1/1/1 | 협력사 | 298건 중 295 (나머지 3 = LG 특례) |
| 1/1/0 | 매입판매 | 45건 **전건 단일** |
| 0/1/0 | 판매처 | 5건 **전건 단일** |

## 9. 이 세션에서 내가 틀렸던 것

1. **"두 달력이 중복이니 통합하자"** → 라인=고객사·근무=사내로 **기준이 다른 별개 달력**이었다.
   통합했으면 당김일자가 통째로 틀어졌다.
2. **"PR_M_WORK 는 WORK_DESC 만 쓴다"** → `prodinfo.py:109` 가 `PROD_RATE` 를 읽어 화면이 죽었다.
   조인 별칭을 따라가지 않고 테이블명이 있는 줄만 봤다.
3. **"SP 6개·7,668줄을 Python 으로 이식해야 한다"** → 테이블명 치환으로 끝났다.
4. **"미러 테이블을 rename 하자"** → 웹이 호출하는 SP 6개가 참조 중이라 깨질 뻔했다.
5. **BOM 9쌍을 볼 때 적용일 축을 안 봤다** → 대표님이 "적용일이 26.10월"이라고 짚어주셨다.
6. **"작업자는 별개 테이블"이라며 파트마스터 전환에서 뺐다** → 파트마스터의 **짝**이라
   한 화면이 두 계보로 갈렸다(§6-3). 쓰기가 있는 그리드였으니 그대로 두면 컷오버에 죽었다.
7. **남은 미러 규모를 SP 없이 셌다** → `PR_M_ITEM` 을 "14곳"이라 적었는데
   실제로는 코드 27 + **웹호출 SP 94곳**이다. 규모 판단이 통째로 틀렸다(§8 실측으로 교체).
8. **검증하면서 데이터를 바꿨다** → `worker_save_all` 이 빈 플래그를 `'0'` 으로 정규화하는 걸
   모르고 "명단 그대로 저장 = 무변화"로 가정, `S1 신선영 반장` 을 **두 번** 바꿔 두 번 복구했다.
   ⟹ 쓰기 검증은 **부작용 없는 시료**(빈값 없는 파트)로 골라야 한다([[testbed-write-cases]]).
9. **"SP 가 0행" 을 테이블 탓으로 볼 뻔했다** → `@as_mat_flag='0'` 으로 물은 **내 인자 실수**였다.
   대표님이 "똑같은 테이블을 사용했을건데 안나오는게 이상한데"라고 짚어 방향을 잡았다.
   ⟹ 결과가 0건이면 **테이블보다 인자를 먼저 의심**한다(SP 파라미터 정의를 sys.parameters 로 확인).
10. **검증 범위를 과하게 잡아 오래 걸렸다**(대표님 지적) → 수십 초짜리 SP 를 10개 조합 돌렸다.
   전환 자체는 4곳 치환에 몇 초다. ⟹ 무거운 SP 는 **시료를 좁혀** 대조한다.
11. **★재고 2종을 "남은 미러"로 올렸다 — 이미 정본으로 확정된 것이었다.**

   짚어 확인하니 `00_MASTER_INDEX.md` C26-3 에 **"잔액이 실시간 현재재고 정본 — 대표 확정"**
