## §2 검토항목

### A. 라우팅 전에 반드시 결정 (3건)

라우팅은 "공정별 착수일 × 경로"를 다루는 기능이다. 아래가 틀린 채로 얹으면
**잘못된 계획 위에 라우팅을 쌓게 된다.**

#### A-1. 원본/당김 2단 구조가 웹에 없다 ★최우선

> 2판의 A-1(당김 미구현)·A-2(일자 접힘)·C-1(`org_plan_ymd` 없음)은
> **하나의 문제였다.** 계획원본 대사(§3-⓪)로 확인.

##### 레거시 구조 — 원본과 결과를 따로 보관한다

```
UPLOAD_PLAN_YMD  =  ORG_PLAN_YMD      ← 엑셀 원본 (실측 100% 동일, 둘 다 보존용)
        │
        ├─ 당김 적용 ─→  PLAN_YMD     ← 실제 계획일자 (실측 77.1% 가 앞당겨짐)
        └─ 당김 적용 ─→  OUTPUT_HM    ← 실제 시각      (실측 67.7% 가 조정됨)
                         ORG_OUTPUT_HM ← 원본 시각
```

##### 웹 현황 — 원본만 있고 결과가 없다

```
nx.plan_dtl.PLAN_YMD  = 엑셀 원본 그대로.  ORG_* 계열 컬럼 자체가 없음.
→ 웹 MIN(PLAN_YMD) = 레거시 ORG_PLAN_YMD   4,396/4,401 (99.9%)  ★업로드는 정확
→ 웹 MIN(PLAN_YMD) = 레거시 PLAN_YMD       1,006/4,401 (22.9%)   당김이 없어서
```

**업로드·파싱은 완벽하다**(제번·수량·모델 100% 일치, §3-⓪).
없는 것은 **당김 로직과, 그 결과를 담을 자리**다.

웹 `partplan.py:30-45` `_compose_assy` 가 **함수 하나로 6·7단계를 겸한다.**

**★1판 정정 — 실제 동작은 "전개 중단"이 아니라 "출력 억제"다**

```python
def rec(item, cq, path):
    for c, q in CH.get(item, []):
        wc = WCEN.get(c, ''); nq = cq * q
        if wc not in path:
            k = (c, wc); out[k] = out.get(k, 0.0) + nq   # 출력만 억제
        rec(c, nq, path | {wc})        # ← if 블록 바깥. 재귀는 안 끊긴다
```

재귀 호출이 `if` **밖**에 있어, 가공처가 중복돼도 하위 전개는 계속된다.
→ SUB 는 `out` 에서 빠지지만 **그 손자는 살아남는다.**
→ 관찰된 "중간 단계만 빠진 기형 전개"와 정확히 일치한다.

⚠ **수정 시 주의**: 재귀까지 건드리면 과교정이다. 6단계용은 `if` 조건만 떼면 된다.

**판정** — 사용자 확인: *"업체면 제일 상위가 맞지만 사내 생산은 하위도 편성돼야 한다.
실적을 각각 잡기 때문."* → **레거시가 맞고 웹이 버그.**

> **결정할 것**: 6단계용/7단계용 전개를 분리할지. 분리하면 레거시와 맞는다.

```sql
-- ① 누적 리드타임(CUM_LT_HR)을 일/시간으로 분해. 1일 = 8시간
UPDATE PR_T_PLAN_PART_S_WORK
   SET PART_PLAN_YMD = dbo.f_get_relative_work_day_of_part(GAGONG_PROC_CODE, PLAN_YMD, 0)
      ,PART_OUTPUT_HM = OUTPUT_HM
      ,PULL_DAY = FLOOR(CUM_LT_HR / 8)
      ,PULL_HR  = CUM_LT_HR % 8

-- ② 시각 정규화 — 점심(12~13)·업무시간(08~17) 밖을 끌어들임
SET PART_OUTPUT_HM='1200' WHERE PART_OUTPUT_HM>'1200' AND <'1300'
SET PART_OUTPUT_HM='0800' WHERE PART_OUTPUT_HM<'0800'
SET PART_OUTPUT_HM='1700' WHERE PART_OUTPUT_HM>'1700'

-- ③ 시간당김이 그날 업무시간을 넘으면 → 하루 더 당기고 전일 17시로
SET PULL_DAY=PULL_DAY+1, PULL_HR=PULL_HR-(가용시간), PART_OUTPUT_HM='17'+분
 WHERE (가용시간) < PULL_HR          -- 가용시간 = 시각-8 (오후면 점심 1시간 제외)
SET PART_OUTPUT_HM='1300' WHERE PART_OUTPUT_HM='1200'

-- ④ 일 단위 당김 — 파트 근무일 기준
SET PART_PLAN_YMD = dbo.f_get_relative_work_day_of_part(GAGONG_PROC_CODE, PART_PLAN_YMD, -PULL_DAY)
 WHERE PULL_DAY > 0

-- ⑤ 남은 시간 당김 — 점심 넘어가면 1시간 더 뺌
SET PART_OUTPUT_HM = CASE WHEN 시각>=13 AND 시각-PULL_HR<13 THEN 시각-PULL_HR-1
                          ELSE 시각-PULL_HR END
 WHERE PULL_HR > 0

-- ⑥ 오전/오후 구분
SET AMPM      = CASE WHEN OUTPUT_HM      <'1200' THEN 'AM' ELSE 'PM' END
   ,PART_AMPM = CASE WHEN PART_OUTPUT_HM <'1200' THEN 'AM' ELSE 'PM' END
```

**핵심 규칙**
- 1일 = **8시간**. `CUM_LT_HR` 를 8로 나눠 일/시간 분해
- 업무시간 **08:00~17:00**, 점심 **12:00~13:00** 제외
- 일 단위 당김은 **파트별 근무일 달력** 기준

#### 근무일 함수 = `dbo.f_get_relative_work_day_of_part(part_code, ymd, N)`

`PR_M_PART_CALENDAR` 에서 **공통 달력을 파트 달력이 덮어쓰고**(LEFT JOIN),
근무일만 세어 N일 당긴 날짜를 반환. `N=0` 이면 그날이 휴무일 때 **직전 근무일로 당김**.

※ 라인 단위 `f_get_relative_work_day_after(line_no,…)` / `f_plan_ymd_hm_proc(…)` 도
확보돼 있으나 그쪽은 4단계(LG INPUT 시각) 계열.

### ⑦ 5단계 품목별생성(I) — 웹과 6가지가 다름 (→ A-1·A-3·B-1)

**사용자가 PBL clicked 원문 제공.** 레거시 핵심 SQL:

```sql
-- 생산계획
INSERT INTO pr_t_plan_item_dtl
SELECT ..., CASE WHEN FIX_LINE_NO>'' THEN FIX_LINE_NO ELSE LINE_NO END, ...
  FROM pr_t_plan_dtl a
  JOIN pr_m_model_bom b ON a.model_no = b.model_no
                       AND a.org_plan_ymd BETWEEN b.make_ymd AND b.to_apply_ymd
  JOIN pr_m_item m      ON b.c_item_code = m.item_code
 WHERE a.plan_ymd >= :ls_plan_ymd
   AND b.make_ymd = (SELECT MAX(make_ymd) FROM pr_m_model_bom t
                      WHERE t.model_no=a.model_no AND t.C_ITEM_CODE=b.C_ITEM_CODE
                        AND a.org_plan_ymd BETWEEN t.make_ymd AND t.to_apply_ymd)

-- 영업계획(같은 단계에서 동시 생성) — a.plan_ymd 기준, sa_t_plan_dtl 원천

```

| 항목 | 레거시 | 웹 | 영향 |
|---|---|---|---|
| 그레인 | `pr_t_plan_dtl` **제번당 1행** | 제번×모델 합산, `MIN(PLAN_YMD)` | A-1 로 흡수(아래) |
| 모델BOM | **INNER JOIN** — 없으면 탈락 | 주문 fallback 으로 살림 | STEP5 2.9배 ★A-3 |
| BOM 유효일자 | **`org_plan_ymd`** 기준 | `plan_ymd` (컬럼 없음) | BOM 버전 오선택 ★A-1 |
| BOM 버전 | `MAX(make_ymd)` **하나만** | 유효한 것 전부 | 현재 0건(위험만) |
| 산출물 | 생산 + **영업계획 2개** | 생산 1개만 | 040 불일치 ★B-1 |

#### `org_plan_ymd` — 웹에 컬럼 자체가 없다 (→ A-1 로 통합됨)

```
실측: 레거시 PR_T_PLAN_DTL 4,401행 중 org_plan_ymd ≠ plan_ymd 인 것 3,395건 (77.1%)
      웹 nx.plan_dtl 의 ORG_ 컬럼 = 없음
```
`org_plan_ymd`(원래 계획일자)는 계획이 당겨지거나 밀려도 **BOM 버전 판정이 흔들리지
않게** 하는 장치다. 77% 가 다른 값인데 웹은 개념 자체가 없어 `plan_ymd` 로 판정한다.

**3판 정정** — 2판은 이 표의 그레인 항목에 "레거시는 행 단위라 일자가 보존된다"고

보존한다(§3-⓪). 따라서 그레인·`org_plan_ymd`·당김은 **하나의 문제**이며 A-1 로 통합했다.

### ⑧ 재고충당 — 스냅샷 vs 실시간 (**실시간으로 결정됨**) (→ C-2)

6단계 SP 는 계획에 **실시간 재고를 충당해 "실제 만들어야 할 양"** 을 계산한다.
순서(SP 주석 그대로):

```
출하실적 적용   → SALE_QTY      (sa_t_sale_dtl, finish_flag='0', 기준일 이전)
  └ 지난 계획수량을 출하수량에서 차감
제품재고 적용   → ASSY_STOCK_QTY (sa_t_item_stock_LAST)
자재재고 적용   → PR_STOCK_QTY   (pr_t_mat_stock_wh_LAST + pu_t_mat_stock_wh_LAST + 스태커)
```
수량환산: `CEILING(LOT_QTY * USE_QTY * PROD_RATE / 100)` — 불량률 반영

#### 차이 1 — 레거시는 `_LAST` 스냅샷, 웹은 실시간 → **웹 유지로 결정**

| 재고 | 레거시가 읽는 `_LAST` | 실시간 원본(웹) |
|---|---:|---:|
| ASSY 완제품 | `sa_t_item_stock_last` 247행 | `SA_T_ITEM_STOCK` 2,681행 |
| 생산파트 | `pr_t_mat_stock_wh_last` 1,497 | `PR_T_MAT_STOCK_WH` 9,928 |
| 자재창고 | `pu_t_mat_stock_wh_last` 2,536 | `PU_T_MAT_STOCK_WH` 7,742 |

**실측: ASSY재고 공통 247품목 중 65건(26.3%)이 스냅샷≠실시간.**
`nx` 에는 `_LAST` 테이블이 **아예 없다.**

**✅ 결정: 웹은 실시간 유지**(사용자 확인 2026-08-26).
→ 이 항목으로 값이 다른 것은 **정상**. 대사 시 제외 대상. `_LAST` 는 만들지 않는다.

#### ★차이 2 — 충당 대상범위(4근무일)

```sql
-- 레거시: 오늘부터 4번째 근무일까지만 충당
select @as_to_ymd = ... FROM HR_M_CALENDAR
        where work_stats in ('1','2','5','6') ... where row_num = 4
where t.PART_PLAN_YMD <= @as_to_ymd
```
실측: 오늘 260826 → **260902 까지만** 충당. 먼 미래 계획에 재고를 당겨쓰지 않는다.
웹: 화면 조회기간(기간 N일) 안의 셀에만 충당 — **제한 개념 자체가 다르다.**

#### ★차이 3 — 충당 정렬순서가 단계마다 다름

```
레거시 출하충당: WORK_ORDER, SPLIT_WORK_ORDER, ASSY_ITEM_CODE, BOM_LEVEL,
                UPPER_ITEM_CODE, ITEM_CODE, PROC_SEQ, PLAN_YMD
레거시 ASSY충당: ASSY_ITEM_CODE, UPPER_ITEM_CODE, ITEM_CODE, GAGONG_PROC_CODE,
                PLAN_YMD, OUTPUT_HM, WORK_ORDER, SPLIT_WORK_ORDER   ← 순서가 다르다
웹            : 단일 _shared() 로 통일
```
→ 레거시는 충당 종류마다 정렬이 다르다. 웹은 통일돼 있어 **같은 재고를 다른 순서로
나눠 쓸 수 있다.** 셀 색상·충당량 불일치의 잠재 원인.

### ⑨ 7단계 협력사계획 — 웹은 6단계를 안 거치고 처음부터 다시 전개 (→ A-2·C-1)

`SP_PR_CREATE_PLAN_협력사계획_생성`(11,307자) 전문 확보.

#### 차이 1 — 입력 원천이 다르다

```
레거시:  PR_T_PLAN_PART_DTL (6단계 산출)  →  BOM 재귀전개  →  PR_T_PLAN_PART_MAT
         └ part_plan_ymd / part_output_hm / part_plan_qty 를 그대로 승계
         └ part_plan_qty / use_qty  (파트수량을 use_qty 로 나눠 원단위 복원)
         └ part_plan_ymd < 기준일 이면 기준일·'0750' 으로 끌어올림

웹:      nx.plan_dtl (업로드 원본)  →  BOM 전개  →  nx.plan_part
         └ 6단계(plan_part_dtl)를 거치지 않는다 ★
```
→ 웹은 6단계에서 계산한 **당김일자·파트수량을 버리고** 처음부터 다시 전개한다.
`nx.plan_part`(97,357행)와 `PR_T_PLAN_PART_MAT`(96,074행)는 행수만 비슷할 뿐
**성격이 다른 산출물**이다.

#### 차이 2 — A-2 컷 버그의 진짜 출처가 여기다

```sql
-- 7단계 필터 (협력사 전용)
where charindex('||' + mat_work_center_code + '||', cum_in_cust_code) = 0
  and not (cust_flag = '0' AND gc_gubun = 'P')
```
레거시는 두 단계의 규칙을 **명확히 분리**한다:

| 단계 | 필터 | 의미 |
|---|---|---|
| 6단계(파트별) | `in_cust_code = ''` (사내) | 사내만 공정편성, **컷 없음** |
| 7단계(협력사) | `charindex(...)=0` | 조상에 같은 가공처면 **컷** |

※ 레거시 원문은 `IN ('','2228')` 이지만 **2228(제이에스)은 지금 없는 업체**.
  옛 데이터용 예외이므로 **웹 이식 시 `= ''` 만 쓰면 된다.**

웹 `_compose_assy` 의 `if wc not in path:` 는 **7단계 규칙**인데, 이 함수 하나로
6단계 성격의 전개까지 처리하면서 **사내 SUB 가 사라졌다**(A-2 의 근본 원인).

#### 그 밖의 7단계 규칙
```sql
-- 최하위만 남긴다(상위 레벨에 같은 자재가 또 있으면 제외)
where not exists (... bom_level > a.bom_level and bom_mat_code = a.bom_mat_code)
-- 사급품은 앵커멤버에서 이미 구했으므로 재귀 중단
-- 수량 = sum(part_plan_qty * cum_use_qty)
-- 일자 = min(part_plan_ymd), 시각 = substring(min(part_plan_ymd+part_output_hm),7,4)
-- 협력사 납기 당김
IIF(C.IN_CUST_CODE>'' AND L.CUST_MAINT_DAY>0, f_get_relative_work_day_doo(...))
   ※ CUST_MAINT_DAY = LINE-NO MASTER 의 '직납품당김일자'
-- 산출물 2개: PR_T_PLAN_PART_MAT(96,074) · PR_T_PLAN_PART_MAT_BY_ITEM(100,951)
```
웹은 `nx.plan_part_mat`(103,328) 하나. `_BY_ITEM` 대응물 없음.
