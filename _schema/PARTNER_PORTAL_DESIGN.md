## 1. ★★가장 급한 결함 — 백엔드에 인증이 없다

### 실측
- 로그인·사용자·비밀번호가 **프론트 JavaScript 안에** 있다(`core.js` `SEED_USERS`, `nx.web_user.udata` JSON).
  ```javascript
  {id:'miraero', pw:'1234', nm:'미래정밀', roles:['협력사'], partner:'미래정밀'}
  ```
- **API 는 누구든 부르면 응답한다.** `Depends`·토큰·세션 검사가 없다.
- 협력사 API 도 **`cust` 를 쿼리 파라미터로 받는다**:
  `GET /api/partner/deliv420?cust=...` — 값만 바꾸면 남의 데이터가 나온다.

### 위험
협력사에게 접근을 열면 **미래정밀이 대원 계획을 그대로 볼 수 있다.** URL 파라미터 하나 바꾸면 된다.
비밀번호도 브라우저에서 그대로 보인다.

### ⟹ 원칙
> **협력사에게 열기 전에 백엔드 인증·소속 강제가 반드시 선행한다.**
> 화면에서 숨기는 것은 보안이 아니다. **서버가 거부해야 한다.**

## 2. 1단계 — 인증 · 소속 강제 (선행 필수)

### 2-1. 저장
`nx.web_user` 를 **행 단위 실테이블로 승격**한다(지금은 `__ALL__` 한 행에 JSON 통째).
```
nx.app_user      user_id · pw_hash · salt · name · utype(내부/협력사) · partner_code · status
                 last_login · fail_cnt · locked_until
nx.app_session   token · user_id · issued_at · expires_at · ip · ua · revoked
```
- **비밀번호는 해시로만 저장**(평문 금지). 기존 평문은 최초 로그인 시 해시로 승격.
- `partner_code` = **거래처코드**(`CM_M_CUST.CUST_CODE`). 지금 `partner:'미래정밀'` 은 **이름**이라 위험하다
  (동명·개명·공백). **코드로 바꾼다.**

### 2-2. 검사
```
POST /api/auth/login    → 토큰 발급(만료 있음)
GET  /api/auth/me       → 현재 사용자·역할·partner_code
POST /api/auth/logout   → 토큰 폐기
```
FastAPI `Depends(current_user)` 로 **전 엔드포인트에 부착**. 무토큰 = 401.

### 2-3. ★소속 강제 (핵심)
협력사 계정이 부르는 API 는 **`cust` 파라미터를 신뢰하지 않는다.**
```python
def scope_cust(user, req_cust=None):
    """협력사면 자기 코드로 **고정**. 내부 사용자만 req_cust 를 쓴다."""
    if user.utype == '협력사':
        return user.partner_code          # 파라미터 무시
    return req_cust
```
- 협력사가 남의 코드를 넣어도 **자기 것만** 나온다.
- 대상: `partner/planstatus` · `partner/deliv420` · `setin/*` · `setstock/*` 등 협력사 노출 API 전부.

### 2-4. 검증 (필수)
- 협력사 토큰으로 **남의 `cust` 요청** → 자기 데이터만 나오는지
- 무토큰 호출 → **401**
- 내부 사용자 → 종전대로 전 협력사 조회 가능(회귀 없음)
- TestBed 에 `[R]` 케이스로 등록

## 3. 2단계 — 협력사 포털 (모바일 웹앱 / PWA)

**네이티브 앱이 아니라 웹앱으로 간다**(대표 동의). 스토어 심사·배포가 없고, 링크만 열면 되고,
지금 웹 코드를 그대로 쓴다. 폰 카메라 QR 스캔도 브라우저에서 된다.

### 화면 4개
| 화면 | 하는 일 | 쓰는 API |
|---|---|---|
| **① 내 계획** | 자기 계획만 · 일자축 · 요청수량/완료수량 | `partner/planstatus`(소속 강제) |
| **② 송장 발행** | 계획에서 납품분 선택 → 송장 생성 → **QR 표시/인쇄** | `setin/issue` — ★`setinreq` 재구현 |
| **③ 내 송장** | 발행분 목록 · 상태 추적 · **출발 처리(20)** | `setin/list` + 상태전이 API(신규) |
| **④ 입고 스캔**(우리 담당자용) | QR 스캔 → 확인 → 입고 | `setstock/scan` → `receive` |

### QR 코드
- 값 = **`barcode_no`**(이미 채번됨). 새 체계를 만들지 않는다.
- 발행 화면에서 QR 렌더 → 협력사가 **인쇄해 상자에 부착**.
- 우리 입고: **폰 카메라** 또는 **기존 바코드 리더기**(리더기는 키보드 입력이라 그대로 동작).

### 신규 필요 API
```
POST /api/partner/depart     송장 출발 처리 (status 10 → 20)   ← 협력사 앱
GET  /api/partner/my         내 계획·송장 요약 (홈 화면)
```

### IQC 분기 — 코드는 이미 있고, 지금은 잠자는 상태
```
insp_flag='1' → 입고 시 status 30(입고대기) → [IQC 승인] → 90(입고완료) → 재고 파생
insp_flag='0' → 입고 즉시 90 → 재고 파생        ← ★지금은 전부 이쪽
```
지금 `insp_flag` 는 1,203건 **전부 `'0'`** 이라 검사 경로가 실행되지 않는다.
**분기 자체는 `setstock_receive` 에 이미 있으므로 건드리지 않는다**(§4-1).
나중에 `insp_flag` 를 채우면 그대로 살아난다.

## 4. 3단계 — 계획 변동 알림

### 감지
계획은 **매일 재편성**된다([[newerp-plan-program-master]]). 그래서 "바뀌었다"를 알려면 **직전 편성과 비교**해야 한다.
```
nx.plan_snapshot_partner(partner_code, plan_ymd, item_code, qty, snap_at)
편성 후 → 직전 스냅샷과 diff → 협력사별 변동(신규/증가/감소/삭제) 산출
```
> ★주의: [[newerp-nxledger-cutover-diagnosis]] 교훈 — 계획 비교는 **같은 기준일끼리** 해야 한다.
> 기준일이 하루만 달라도 80%/100%/77% 로 출렁인다. 스냅샷에 **기준일을 함께 저장**한다.

### 전달
| 방식 | 장단 |
|---|---|
| **웹 푸시(PWA)** | 앱 설치 없이 폰 알림. iOS 는 홈화면 추가 필요 |
| **문자/알림톡** | 확실히 도달. 건당 비용 |
| **포털 내 배지** | 무료·확실. 다만 열어봐야 안다 |

**권고: 포털 배지 + 웹 푸시**로 시작하고, 중요 변동만 알림톡을 얹는다.

## 5. 순서와 이유

```
1단계  인증 · 소속 강제        ← 이게 없으면 2·3단계가 위험하다
2단계  포털 4화면 + QR
3단계  변동 감지 + 알림
```

**1단계를 건너뛰면 안 된다.** 협력사에게 URL 을 주는 순간 남의 데이터가 열린다.

| # | 물음 | **확정** |
|---|---|---|
| 1 | 계정 단위 | **협력사별 1개** (업체 = 계정 1:1) |
| 2 | 송장 발행 주체 | **협력사가 직접 발행.** 단 **계획서에 지정된 것만** |
| 3 | 포털 대상 구분 | **거래처에 필드를 등록해 관리** |

### 2번 확정의 함의 — 발행 화면은 이미 있고 계획 제한도 걸려 있다
`POST /api/setin/issue` 가 **이미 계획분만 발행**하도록 막고 있다:
```sql
WHERE sheet_no=? AND remarks='PLAN_COMPOSE' AND status IN ('00','10')
```
`PLAN_COMPOSE` = **계획에서 자동 편성된 송장**. 협력사가 임의로 만들 수 없다.
⟹ 대표 요구("계획서에서 지정된 것만 발행")가 **그대로 구현돼 있다.**

**★`setinreq`(거래명세서 발행-바코드)를 내린 사유 = 구현이 잘 안 됐다**
(대표 확인 2026-08-29). 커밋 `088be2d` 에는 "요청"만 적혀 있었다.
⟹ **이번 작업의 핵심 대상이 바로 이 화면이다.** 되살리는 게 아니라 **다시 만든다.**

무엇이 부족한지는 착수 전에 실행해 보고 확정한다(추측 금지). 지금까지 코드로 확인한 것:
- 화면 골격·상태 뱃지(`00요청 10발행 20출발 30입고대기 40검사중 90완료 99반품`)는 있다.
- `setin/list` → 체크 → `setin/issue`(배치 QR 채번) 흐름도 있다.
- ☐ **QR 렌더·인쇄가 없다**(발행만 하고 코드를 눈에 보여주지 않는다).
- ☐ 협력사 관점 화면이 아니다(우리 담당자용 그리드).

| 화면 | 상태 | 성격 | 평가 |
|---|---|---|---|
| **`deliv420` 거래명세서 발행** | 메뉴 있음 | 레거시 `w_pr_outside_420` 재현 | ✅ **대표 확인: "작동이 정확하다 · 레거시를 잘 구현했다"**(2026-08-29) |
| **`setinreq` 발행(바코드)** | **내려놓음**(`core.js:161` 주석) | QR/바코드 | ★**구현이 잘 안 돼서 내림**(대표) — **이번에 다시 만들 대상** |
| `delivedit` 거래명세표 수정 | 신규(Dyun) | 수량수정·재발행 | |

> ※대표 화면에는 이 메뉴가 보였으나 `feat/partner-portal`·`zt/main` 코드 모두 주석 처리 상태다
> (실측 2026-08-29). 브라우저 캐시 또는 다른 세션 미푸시분. 손대기 전에 확인할 것.

### 3번 — 포털 대상 필드 (거래처에 등록·관리)
레거시 `CM_M_CUST` 는 컷오버에 죽는다. ⟹ **클린 쪽에 둔다.**
```
nx.partner_portal   cust_code(PK) · portal_use('1'/'0')   포털 개방 여부
                    noti_kind('T' 알림톡 / 'W' 웹)        알림 채널
                    noti_phone · noti_name                 알림톡 수신처
                    upd_user · upd_dt
```
**관리 화면** = 기준정보에 「협력사 포털 관리」 신설.
목록에서 **체크로 켜고 끈다**(대표가 직접 지정). 자동 판별 없음.

> 왜 별도 테이블인가 — `CM_M_CUST` 는 레거시 미러라 **매일 sync 가 통째로 덮는다**
> (`r_delta_sync` do_full = TRUNCATE + 재적재). 거기에 우리 필드를 넣으면 **매일 지워진다.**
> 단가 마스터·재고 잔량에서 이미 겪은 문제와 같은 구조다.

### 5번 확정 — 알림 채널 2원화 · **대상은 대표가 직접 지정**
| 대상 | 채널 |
|---|---|
| 대표가 지정한 협력사(주로 절삭) | **알림톡** |
| 나머지 | **웹**(포털 배지 + 웹푸시) |

> **★자동 판별하지 않는다**(대표 지시 2026-08-29: *"그 협력사들은 내가 지정해줄게"*).
> `CUST_TYPE='6'`(절삭-협력사)이 **29곳**으로 잡히긴 하지만, 그걸 조건으로 쓰지 않는다.
> **분류를 알림 조건에 겹쳐 쓰면 분류를 바꿀 때 알림이 딸려 바뀐다.**
> ⟹ 거래처마다 **켜고 끄는 전용 필드**로 관리하고, **화면에서 대표가 직접 지정**한다.
> (참고로 6번에 `가공반(사내)` 같은 내부 조직도 섞여 있어 자동 판별은 위험하다.)

**웹푸시 실제 동작**(대표 질문 "핸드폰에 실제로 떠?"):
- **안드로이드** — 브라우저를 닫아도 알림이 뜬다. 앱과 동일.
- **아이폰** — **홈 화면에 추가**해야 알림이 온다. 사파리로만 보면 안 온다.
  ⟹ 아이폰 협력사에는 "홈 화면에 추가" 1회 안내가 필요하다.

### 4-1. IQC (수입검사) — **지금은 넣지 않고, 나중에 붙일 자리만 남긴다** (대표 확정 2026-08-29)

**실측 — 지금 안 쓰고 있다**
```
nx.QA_T_CUST_IQC_HEAD   3,232행 · 기간 210616 ~ 220317   ← 2022년 3월에 멈춤
nx.set_input_req.insp_flag   1,203건 **전부 '0'(무검사)**
nx.item 검사 여부 컬럼        없음
```
판정 컬럼은 `QA_T_CUST_IQC_HEAD.RESULT_OK`('1' 합격 3,230 / '0' 2).
웹 `qc.py` 는 **조회 전용**(`/api/qc/iqc/list`·`detail`) — 판정 쓰기 없음.

**대표 지시**: *"수입검사 부분은 추후에 추가될 수 있도록 해줘."*

#### ⟹ 설계 원칙 — 나중에 붙일 수 있게 **자리를 비워 둔다**
지금 IQC 를 구현하지 않는다. 그러나 **나중에 넣을 때 기존 코드를 뜯지 않아도 되게** 짠다.

| 남겨 둘 것 | 지금 | 나중에 |
|---|---|---|
| `set_input_req.insp_flag` | **필드 유지**(전부 `'0'`) | 값만 `'1'` 로 채우면 검사 대상이 된다 |
| 상태 `30 입고대기` · `40 검사중` | **상태값 유지**(안 쓰지만 지우지 않음) | 그대로 되살아난다 |
| `setstock_receive` 의 분기 | **코드 유지** — `insp=='1'` 이면 30, 아니면 90 | 조건이 이미 있으므로 **수정 없이 동작** |
| IQC 승인 API | 없음 | `POST /api/qc/iqc/approve` 신설 → 30/40 → 90 → 재고 파생 |

**핵심**: `setstock_receive` 에 **이미 분기가 들어 있다.**
```python
newstat = "30" if insp == "1" else "90"   # 검사품=입고대기, 일반=입고완료
```
⟹ **지금은 `insp_flag` 가 전부 `'0'` 이라 모두 즉시 입고완료(90)** 로 흐른다.
   나중에 검사를 도입하면 **`insp_flag` 를 `'1'` 로 채우는 것만으로** 이 분기가 살아난다.
   **입고 로직을 다시 건드릴 필요가 없다.**

#### 나중에 도입할 때 정해야 할 것 (지금 결정하지 않음)
1. **검사 대상 판별 기준** — 품목별 / 협력사별 / 건별 중 무엇으로 `insp_flag` 를 채울지
2. **검사 결과 기록처** — 레거시 `QA_T_CUST_IQC_*` 를 계속 쓸지, 클린(`nx.qc_*`)으로 갈지
   > ★컷오버 후 레거시는 죽는다(`CLAUDE.md` §1-9-1). **새로 만들면 클린으로 간다.**
3. **승인 화면** — 품질 메뉴(`수입검사(IQC)조회`)를 조회 전용에서 **판정 가능**으로 승격할지
4. **40(검사중) 을 쓸지** — 30(입고대기) → 90 으로 바로 갈지, 40 을 거칠지

#### 지금 지켜야 할 것 (중요)

- 새로 만드는 화면·API 는 **상태 코드 전체(00·10·20·30·40·90·99)를 그대로 다룬다.**
  지금 안 나오는 상태라도 **표시·필터에서 빼지 않는다.**
- 입고 흐름을 단순화한다고 **`setstock_receive` 의 `insp` 분기를 없애지 말 것.**
