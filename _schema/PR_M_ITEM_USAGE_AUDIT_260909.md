# PR_M_ITEM 사용처 전수 감사 (2026-09-09)

> 대표 지시 **"pr_m_item 보자 어디사용중인지"**.
> `nx.PR_M_ITEM`(미러)을 실제로 읽는 곳을 코드·SP 양쪽에서 전수로 세고,
> 클린 `nx.item` 으로 전환할 때 무엇이 걸리는지까지 실측했다. **조사만. 변경 없음.**

---

## 0. 세 줄 요약

- **웹이 실제로 미러를 읽는 곳 = 코드 35곳 + SP/함수 30개(162줄).**
  나머지 SP 191개(1,183줄)는 레거시 전용이라 웹이 안 부른다 — **컷오버 대상이 아니다.**
- **컬럼은 겁먹을 규모가 아니다.** 미러 107컬럼 중 웹 도달 SP 가 실제로 읽는 건 **21컬럼뿐**.
  그중 11은 `nx.item` 에 그대로 있고, 7은 **이름만 다르고 값은 동일**, 3은 **미러도 비어 있다**.
- ⟹ **호환뷰 `nx.v_pr_m_item` 하나로 대부분 끝난다.** 다만 **품명·소분류에 실제 값 차이**가 있어
  그건 뷰가 아니라 **판단이 필요한 데이터 문제**다(§4).

## 3. ★난이도의 실체 — 컬럼은 21개뿐이다

§8 초안에 "`nx.item` 60컬럼 / 미러 107컬럼 — 뷰에 무엇을 넣을지 정해야" 라고 적었는데,
**107 을 다 볼 필요가 없었다.** 웹 도달 SP 가 실제로 읽는 컬럼은 21개다.

| 미러 컬럼 | SP수 | 클린 대응 | 값 대사 |
|---|---:|---|---|
| `ITEM_CODE` | 266 | `item_code` | — |
| `IN_CUST_CODE` | 187 | `in_cust` | **✔ 24,154행 완전일치** |
| `WORK_CODE` | 167 | `work_code` | (동명) |
| `PROD_RATE` | 147 | `prod_rate` | (동명) |
| `ITEM_CLASS` | 27 | `item_class` | (동명) |
| `ITEM_SPEC` | 24 | `item_spec` | (동명) |
| `METAL_GUBUN` | 22 | `metal_gubun` | (동명) |
| `ITEM_DIAM` | 18 | `diam` | **✔ 숫자기준 불일치 0** |
| `ITEM_THICK` | 16 | `thick` | **✔ 숫자기준 불일치 0** |
| `ITEM_LENGTH` | 16 | `length` | **✔ 숫자기준 불일치 0** |
| `ITEM_DESC` | 14 | `item_name` | **⚠ 27건 차이** → §4 |
| `ITEM_LGROUP` | 11 | `lgroup` | ⚠ 1건 |
| `ITEM_SGROUP` | 11 | `sgroup` | **⚠ 98건 차이** → §4 |

| `GC_GUBUN` | 6 | 없음 | **미러 전체 NULL** |
| `LG_WEIGHT` | 2 | 없음 | **미러 전체 NULL** |

### ★치수 3종의 "불일치 10,400건"은 표기 차이였다

문자열로 비교하면 `0.0000` vs `0` 때문에 1만 건이 어긋난 것처럼 보인다.
**`float` 로 캐스팅해 비교하면 불일치 0.** 여기서 멈췄으면 "치수가 다 틀렸다"고 오판할 뻔했다.

⟹ **값 대사는 타입을 맞춰서 한다.** 문자열 비교는 거짓 불일치를 만든다.

### `SILVER_SOLDER`·`GC_GUBUN`·`LG_WEIGHT` 는 클린에 만들 필요가 없다

미러조차 비어 있다(GC_GUBUN·LG_WEIGHT 는 24,154행 **전부 NULL**).
호환뷰에서 `CAST(NULL AS ...)` 로 형만 맞춰 노출하면 된다. 데이터 이관 대상이 아니다.

## 4. ★뷰로 안 되는 것 — 판단이 필요한 데이터 차이

여기가 이 전환의 **유일한 진짜 쟁점**이다. 이름 매핑이 아니라 **어느 값이 맞느냐**의 문제다.

### 4-1. 품명 27건 — 클린이 "정규화된 영문명", 미러가 "현장 표기"

```
1MPC0502018   미러=[사급에 포함된 스크류]      클린=[Screw,Machine]
3A00375E      미러=[SOCKET(Ø12.7)]         클린=[Socket,Flare]
3H01582A      미러=[200mm]                 클린=[Tie]
4A00114C      미러=[동T(Ø22.2-3)]           클린=[Tube,Connector]
5006AR4091H   미러=[Cap(Ø12.7/BLUE)]       클린=[Cap]
AJR30133610   미러=[Tube Assembly,Reverse] 클린=[AJR30133610]   ← 클린이 품번 그대로(품명 없음)
AJR33796526   미러=[Tube Assembly, Capillary] 클린=[Tube Assembly,Capillary]  ← 쉼표 뒤 공백만 차이
```

세 부류가 섞여 있다 —
① **쉼표 뒤 공백**만 다른 것(무해) ② 클린이 **정규화 영문명**(더 정확) ③ 클린이 **품번을 그대로 품명에 넣은 것**(결손).

⚠**주의**: `common.py` L881 에 **"레거시 서식 그대로 찍는 출력물은 라이브 `ITEM_DESC` 원품명으로 나와야 한다"**
라고 이미 적혀 있다. **출력물 계열은 미러 품명이 정답인 경우가 있다.** 일괄 교체하면 안 된다.

### 4-2. 소분류 98건 — 클린이 **의도적으로 다르게** 분류한 것

```
1% 용접봉 / 2% / 3% / 30% 용접봉   미러=[]      클린=[240]
3H00815 계열                      미러=[230]   클린=[240]
12.7로용접링 · 19.05로용접링         미러=[910]   클린=[230]
1MPC0502018                       미러=[993]   클린=[910]
```

**240 = 용접봉**은 우리가 만든 코드다(`_KINDMAP_EXT`, 2026-08-27).
미러엔 빈값이거나 230(부자재)으로 뭉뚱그려져 있다. ⟹ **클린이 맞다. 미러로 되돌리면 안 된다.**
`_MAT_SGROUP` 에 240 이 들어 있어 자재조회 대상 판정에도 쓰인다.

### 4-3. 행수 — 클린이 1,249행 많다

```
라이브 PR_M_ITEM 24,154  =  미러 nx.PR_M_ITEM 24,154   (미러는 최신 상태)
클린 nx.item 25,403
  미러에만 있는 품목 = 0
  클린에만 있는 품목 = 1,249    ← 웹에서 등록했거나 우리가 추가한 것
```

**미러가 클린의 부분집합**이다. 즉 전환해도 **잃는 품목이 없다**.
반대로 **미러를 계속 읽으면 웹 등록 1,249품목이 안 보인다** — 이게 미러를 쓰면 안 되는 실제 이유다.
(§6-7 가공바코드에서 자도번 981종이 `nx.item` 에 없다고 적었는데, 그건 **반대 방향** —
`PR_T_INDI_CUTTING` 의 옛 전표에 남은 폐번이라 양쪽 다 없다. 별건.)

## 5. 권고 — 이렇게 하면 된다

### 5-1. 호환뷰 `nx.v_pr_m_item` (미러 모양 그대로)

달력·WORK류·라인마스터에서 쓴 방식과 같다. **컬럼명·형식을 미러와 똑같이** 노출하면
SP 안에서 **테이블명 한 단어만** 바꾸면 되고 되돌리기도 쉽다.

```sql
CREATE VIEW nx.v_pr_m_item AS
SELECT item_code AS ITEM_CODE, item_name AS ITEM_DESC, item_spec AS ITEM_SPEC,
       lgroup AS ITEM_LGROUP, sgroup AS ITEM_SGROUP, in_cust AS IN_CUST_CODE,
       diam AS ITEM_DIAM, thick AS ITEM_THICK, length AS ITEM_LENGTH,
       work_code AS WORK_CODE, prod_rate AS PROD_RATE, item_class AS ITEM_CLASS,
       metal_gubun AS METAL_GUBUN, unit AS UNIT, cost_gubun AS COST_GUBUN,
       make_type AS MAKE_TYPE, proc_gubun AS PROC_GUBUN, sagub_stock_flag AS SAGUB_STOCK_FLAG,
       CAST(NULL AS varchar(2))  AS SILVER_SOLDER,   -- 미러도 24건뿐
       CAST(NULL AS varchar(1))  AS GC_GUBUN,        -- 미러 전체 NULL
       CAST(NULL AS float)       AS LG_WEIGHT        -- 미러 전체 NULL
  FROM nx.item;
```

★**타입을 미러와 맞출 것.** `nx.item` 은 `diam` 이 decimal 인데 미러는 float 인 식으로 다르면
SP 안 비교·반올림이 미묘하게 달라진다. 뷰에서 `CAST` 로 맞춘다.

### 5-2. 순서 — 데이터 판단 먼저, 코드 나중 (달력에서 배운 것)

1. **§4-1 품명 27건**을 대표님과 정리 — 특히 `AJR30133610` 처럼 **클린 품명이 품번인 것**은 채워야 한다.
   출력물 계열(`common.py` L881)은 미러 품명이 정답일 수 있으니 **그 경로는 예외로 남길지 결정**.
2. **§4-2 소분류 98건은 손대지 않는다**(클린이 맞다).
3. 뷰 생성 → **SP 30개 치환** → **코드 35곳 치환** → 화면 대조.

### 5-3. 덩어리부터 — 작은 것 먼저가 아니다

| 순서 | 대상 | 왜 |

## 6. 이번 조사에서 내가 틀린 것

1. **`nx` 스키마만 뒤져 "모듈 24개"라고 봤다** — SP 본체는 `dbo` 에 있다(398개).
   하마터면 "SP 참조 1개뿐"이라고 보고할 뻔했다. ⟹ **스키마를 가정하지 말고 둘 다 본다.**
2. **문자열로 값 대사를 해 치수 1만 건이 어긋난 줄 알았다** — `float` 캐스팅하니 **불일치 0**.
   ⟹ **타입을 맞춰 비교한다.**
3. **별칭(`a.`·`m.`)으로 컬럼을 세서 `PLAN_QTY`·`WORK_ORDER`·`CALENDAR_YMD` 같은
   남의 테이블 컬럼이 섞여 들어왔다** — 실제 `PR_M_ITEM` 컬럼만 남기니 34종 → **10종**.
   ⟹ **별칭은 재사용된다. 테이블 실제 컬럼으로 교차검증한다.**
